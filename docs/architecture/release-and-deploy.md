# Release and deploy

How Collector is built into an image, published, deployed and kept safe: the container image, the CI workflow that builds and publishes it, release tags, the cleanup of the registry, the Compose and Kamal deployment paths, the request body limit, the stored import upload's retention, backup and restore of an instance, and the proof that a build upgrades the previous release. This is the current truth; the specs it distils record what each feature promised when it shipped (see Sources and the [specs index](../specs/README.md)). The operator's procedures are in `README.md` ("Self-hosting", "Backup and restore") and [`docs/releasing.md`](../releasing.md); this document holds the rules those procedures follow.

## Scope

- The CI workflow `.github/workflows/ci.yml` (the `checks`, `rspec`, `ci`, `image` and `publish` jobs), Dependabot's configuration (`.github/dependabot.yml`), the daily audit workflow `.github/workflows/advisory-audit.yml` (spec 036), and the release tags, channels and labels (spec 001 FR-4; spec 012; [ADRs 0008–0010](../adr/README.md)). `bin/ci` and `config/ci.rb` are a single definition kept in CLAUDE.md's Commands (spec 001 FR-3; see Neighbours); its groups and the RSpec shards, with `lib/collector/ci_groups.rb`, `lib/collector/ci_shard.rb`, the run-time log `spec/support/runtime_log.txt` and `script/ci/record_runtime_log`, are here (spec 035 decisions 4–8). So are the `bin/ci checks` steps for YARD and the comment ratchet, `script/yard/comment_ratchet.rb` (spec 054 decision 2; spec 056).
- Releasing and going public: `docs/releasing.md` (spec 012 Story 7).
- The build facts the image carries and the app reads: the three build arguments, what each trigger passes, the reader `Collector::BuildFacts` and its spec helper, and the smoke check (spec 084). The licence line they feed is in [catalog core](catalog-core.md).
- The cleanup of untagged package versions: `.github/workflows/ghcr-cleanup.yml`, `bin/ghcr-cleanup`, `lib/collector/ghcr_cleanup.rb` (spec 013; [ADR 0011](../adr/0011-own-ghcr-cleanup-script.md)).
- The two deployment paths: `compose.yaml`, `config/deploy.yml`, and the README's Self-hosting section (spec 001 FR-5, FR-6; spec 012 FR-4, FR-5).
- The request body limit at every layer that receives a body (spec 025 decision 6).
- The stored import upload as an operational matter: where it lives, how long, its sweep and the gate on Active Storage's routes (spec 028 decisions 8 and 9; [ADR 0022](../adr/0022-stored-import-upload-retention.md)).
- Backup and restore of an instance: `backup:create`, `backup:restore`, `lib/collector/backup/`, `bin/backup-smoke`, `docs/backup-restore.md` (spec 030; [ADR 0024](../adr/0024-backup-with-vacuum-into.md)).
- The upgrade proof: `bin/upgrade-smoke`, `script/upgrade/` (the release resolution, the migration guard, the comparison, the seeds, the two yml files), and the workflow's Ruby setup and `Upgrade smoke test` steps (spec 031; [#42](https://github.com/plainprogrammer/Collector/issues/42)).

**Neighbours:**

- **Development environment** (stack, `bin/setup`, `bin/ci`, the Claude Code hooks, worktrees, dev ports, libvips in development) has no area doc; its facts stay in CLAUDE.md, where an agent needs them first (specs 001 stack, CI and hooks parts, 003, 014; spec 027 OD3 and D2). ## Glossary

- **Group (of `bin/ci`):** the steps one `bin/ci` argument runs: none for all of them, `checks` for every step but RSpec, `rspec` for the whole suite, `rspec N/M` for one shard; each starts with setup (spec 035 decision 4).
- **Shard:** shard N of M is the N-th of M groups of spec files formed from the run-time log, run in one RSpec process; the M shards of one commit hold every spec file exactly once (spec 035 decision 6, AC-1.5).
- **Run-time log:** `spec/support/runtime_log.txt`, committed, one `path:seconds` line per spec file from a serial run (spec 035 decision 6).
- **Release:** a git tag `vX.Y.Z`, optionally with a pre-release suffix `-<suffix>` where the suffix matches `[0-9A-Za-z.-]+` (spec 012 Terms; `docs/releasing.md`).
- **`main` channel:** the images published from every push to `main`: `edge` and `sha-<7-character sha>` (spec 012 Terms; [ADR 0009](../adr/0009-image-tags-and-release-channels.md)).
- **Manifest list:** one image name that resolves to the right architecture on pull; here always exactly `linux/amd64` and `linux/arm64` (spec 012 AC-2.1).
- **Build / publish:** a *build* produces one per-architecture image and, on `main` and release tags, pushes it by digest, untagged. *Publish* is creating the tagged manifest list from those digests (spec 012 Terms).
- **Version (of the package), tagged, untagged, referenced:** one entry in the package's version list. A version is *tagged* when the packages API reports a tag for it; a digest is *referenced* when a tagged manifest list names it as a child (spec 013 Terms).
- **Orphan unit:** an untagged manifest list with those of its children that are in the version list, untagged and unreferenced, or any other untagged, unreferenced version alone; units that share a member are one unit. Its age is its newest member's. It is *past the grace period* when strictly more than 7 days old (spec 013 Terms; `Collector::GhcrCleanup::GRACE`).
- **Instance, volume:** one running Collector and its `storage/` volume, `collector_storage` mounted at `/rails/storage`, holding the primary, prices, queue, cache and cable SQLite databases (spec 001 FR-1, FR-5; [ADR 0016](../adr/0016-sqlite-in-every-environment.md); spec 081 decision 1, [ADR 0029](../adr/0029-prices-database-held-by-the-backup.md)). The prices database's own rules are in [prices](prices.md).
- **Fresh volume:** a volume that holds none of the five databases and none of their `-wal`, `-shm` or `-journal` files (spec 030 Terms, decision 6; spec 081 decision 8).
- **Backup, snapshot:** one file (`collector-backup-YYYYMMDDTHHMMSSZ.tar.gz`) holding a manifest, `primary.sqlite3` and `prices.sqlite3`, each a consistent copy of its database at one moment, the two taken one after the other (backup format version 2; spec 030 Terms, decision 5; spec 081 decisions 6 and 7; ADR 0024, ADR 0029). Version 1, from earlier releases, holds the primary only.
- **Stored upload:** the previewed import file, kept for an hour so that applying is one click; **orphan blob:** an Active Storage blob that carries the import-upload marker, has no attachment and is older than `ImportUpload::ORPHAN_GRACE` (spec 028 decision 9; ADR 0022).
- **Operator:** the person who runs the instance and has a shell on its host or container (spec 030 Terms).

## Invariants

### The pipeline and the tags

- **One CI definition.** `bin/ci` (`config/ci.rb`) is what runs locally, in the pre-push hook and in the workflow, which runs it as groups: the `checks` job runs `bin/ci checks` and each `rspec` shard runs `bin/ci rspec N/M`. The pre-push hook runs the full `bin/ci`, or `bin/ci checks` for a documentation-only branch. Every step stays in `config/ci.rb`; the workflow and the hook name groups, never a check (spec 001 FR-3, FR-4; spec 035 decisions 3, 4, 5, AC-2.1, AC-3.3, which supersede spec 001 AC-2.5's single check job; `.github/workflows/ci.yml:20-34`, `ci.yml:38-68`).
- **The comment ratchet is a `bin/ci checks` step** (`ruby script/yard/comment_ratchet.rb`, after the YARD step): it fails a branch that adds or changes a judged public class, module or method that has no summary, and judges only what the branch changed, never total coverage, so the code it doesn't touch passes whatever its documentation (spec 056 Goals, decision 1 to 6, AC-3.3, AC-4.1; issue [#264](https://github.com/plainprogrammer/Collector/issues/264); ADR 0027's room for a later check; `script/yard/comment_ratchet.rb`, `config/ci.rb:31`). It runs on the commits in GitHub and on the working tree locally, so an untracked, not-ignored file in scope can fail a local run that CI wouldn't see (spec 056 Goals, AC-1.12). Its rules:
  - **What it judges** (decisions 1 and 3): the public classes, modules and instance and class methods (`class << self` included) of the `.rb` files under `app/models/` (concerns included), `app/helpers/`, `app/*/concerns/`, `lib/` and `spec/support/` (`YardRatchet::Scope::PATTERNS`); not controllers, jobs, mailers, channels or any other path, and never constants, attribute methods, `initialize`, private or protected methods, or what YARD doesn't register (`scope`, `define_method`, `delegate`, methods inside `RSpec.configure` or shared-context blocks). A `Struct.new` or `Data.define` held in a constant is a class and is judged. An override is judged like any method.
  - **What counts as a comment** (decisions 2 and 3, AC-1.9, AC-1.10, AC-1.15): a summary, any text before the first tag. Tags alone, `# @private` and `# @!visibility private` don't count; `# @api private` does, with or without text, and on a class or module it covers the members YARD scopes under it. A `(see Other#method)` comment counts once YARD resolves it to a scoped method that has a summary. `@param` and `@return`, and whether a comment is current or says why, are not checked; they stay with reviews, and a failed run says so (decision 6, AC-3.2, AC-3.6).
  - **What "changed" means** (decision 4, AC-1.4 to AC-1.8, AC-2.3 to AC-2.9): a text comparison with the base, not a diff. A method is changed when it is new by its qualified name (`Widget#spin`) across the base's scoped files, or when the text of its extent (its own comment through its `end`) differs; a reformat, an edit that only deletes lines, and deleting its comment are changes, while a method moved within a file or between files of one class, a deletion next to it and a rename of a file are not. A class or module is changed when it is new (judged once however many files open it, from a registry of every scoped file at the head) or when its comment or its opening line changes; an edit to a member does not change it, and a `module` wrapper the base already defines is not judged. A comment above only the outer `module Collector` line documents `Collector`, not the class the file defines.
  - **The base** (decision 5, AC-3.3, AC-3.4, AC-3.7): `git merge-base HEAD origin/main`, whatever `HEAD` is, so GitHub's detached pull request merge commit and a tag push are judged by the same rule, unlike `Collector::PushScope`, which refuses a detached `HEAD`. It fails, and never passes, when `origin/main`, the merge base or the full history is missing or the clone is shallow, naming what to fetch, and when a changed file YARD can't parse; an unchanged one YARD can't parse is ignored. After a merge of `main` into the branch, what `main` brought in isn't judged.
  - **The history it needs:** the `checks` job's checkout has `fetch-depth: 0`, which the check depends on and which stays (decision 5, AC-4.9; `ci.yml:23-26`, `spec/script/upgrade/files_spec.rb`).
  - **Output and budget** (decisions 5 and 6, AC-3.1, AC-3.5, AC-4.3): one line per offender (`path:line: Name has no comment (added|changed)`, with a hint for a class nested in another namespace), a count, the rule's path (`YardRatchet::RULE`), and nothing written into the checkout. The budget is 30 s; it measured about 0.3 to 0.4 s on a branch that changes no judged file, and 1.07 s for 165 files added against an empty base (spec 056 `verification.md`; the pull request's `checks` log is recorded there when it exists).
- **`bin/ci` takes one optional group, checked before any step runs.** With no argument it runs every step serially in its old order (setup, the migration guard, RuboCop, the YARD build, the comment ratchet, Brakeman, bundler-audit, the importmap audit, RSpec), the suite in one process; `checks` runs all but RSpec; `rspec` runs setup and the whole suite; `rspec N/M` (1 ≤ N ≤ M) runs setup and shard N of M. Any other argument exits non-zero before any step and names the accepted forms (spec 035 decision 4, AC-1.1–AC-1.3, AC-1.6; spec 054 decision 2, AC-2.3; `lib/collector/ci_groups.rb`, `config/ci.rb:5-9`). Locally `bin/ci` and the hook stay serial; only GitHub shards (spec 035 decision 2).
- **Every RSpec run of `bin/ci` prints the 10 slowest examples** (`--profile 10`), in a plain run, `bin/ci rspec` and each shard, so a regression like spec 035's parity example shows in every log. It is not a gate: no exit status depends on it (spec 035 decision 8, AC-1.9; `config/ci.rb:12`, `config/ci.rb:21`).
- **Shards come from the committed run-time log.** `Collector::CiShard` forms shard N of M through `parallel_tests`' own grouping (`ParallelTests::RSpec::Runner.tests_in_groups`) by run time from `spec/support/runtime_log.txt`, with `allowed_missing_percent: 100`; without the log it groups by file size and `bin/ci` prints that balance may be worse. The groups depend only on the commit and the log, never on the machine's cores, and the M shards hold every spec file exactly once (spec 035 decision 6, AC-1.5, AC-2.6; `lib/collector/ci_shard.rb`, `config/ci.rb:19`). A stale log changes only balance, never which files run: a file missing from it gets the average time and a deleted one is ignored (spec 035 decision 6, NFR Reliability). Refresh it with `script/ci/record_runtime_log`, a serial run that keeps only the `path:seconds` lines, sorted by path, when shard times on GitHub differ by more than a minute or spec files are added or removed in bulk (spec 035 decision 6; `script/ci/record_runtime_log`).
- **Each shard prints its seed and a replay before its examples run**: the file count, the grouping, the seed (`SEED`, or a random one chosen before the run) and `CI=true bin/rspec --seed S --profile 10 <files>`, which runs the same files in the same order with the same seed. `CI` is set because `config/environments/test.rb` eager-loads when it is present, as it is in `CI.run` and on GitHub. A shard runs in one process against `storage/test.sqlite3` (spec 035 decision 6, AC-1.4, AC-2.3; `config/ci.rb:14-22`, `lib/collector/ci_shard.rb:25`).
- **Nothing is published unless every `bin/ci` group passed on the same commit.** The aggregate `ci` job needs `checks` and `rspec`, runs unless the run was cancelled (`if: ${{ !cancelled() }}`), has no checkout and fails unless both succeeded; the `image` job needs `ci`, and `publish` needs `image`; so a failed check or shard pushes nothing, and a cancelled run builds no image (spec 012 FR-1, AC-3.4; spec 035 decision 5, AC-2.1, AC-2.2; ADR 0010; `ci.yml:71-80`, `ci.yml:86`, `ci.yml:211`). The shards run with `fail-fast: false`, so one failing shard doesn't stop the others, and each uploads its failure screenshots as `screenshots-N` (spec 035 decision 5, AC-2.3; `ci.yml:41-44`, `ci.yml:62-68`).
- **A pull request builds both architectures and pushes nothing:** no tag, no digest, no registry cache. The registry login, the push by digest and the `publish` job are all conditioned on the event not being a pull request; the build cache is the CI service's own (`type=gha`) (spec 012 FR-1, AC-4.2, AC-4.3, NFR Security; `ci.yml:170`, `ci.yml:180`, `ci.yml:212`).
- **Only the workflow pushes to the public image.** The maintainer's Kamal deploys use `--skip-push` (spec 012 FR-1, FR-5; ADR 0009 Consequences). `packages: write` is granted only to the `image` and `publish` jobs; the top-level permission is `contents: read`, and `checks`, `rspec` and `ci` have no permissions of their own (spec 012 FR-1, NFR Security; spec 035 NFR Security; `ci.yml:12-14`, `ci.yml:88-90`, `ci.yml:214-216`).
- **Triggers.** The workflow runs on pull requests, on pushes to `main`, and on tags matching `v[0-9]+.[0-9]+.[0-9]+` or `v[0-9]+.[0-9]+.[0-9]+-*`. Any other tag runs nothing. That a release tag is annotated and on `main` is procedure, not checked (spec 012 AC-3.6, AC-7.1; ADR 0009; `ci.yml:3-10`).
- **Tags follow ADR 0009's table** ([What each trigger publishes](../releasing.md#what-each-trigger-publishes)); all tags of one run resolve to one manifest list. A `0` tag is never published for `0.y.z`; `latest` moves only on a stable release tag, never on a pre-release or the `main` channel (spec 012 FR-2; ADR 0009; `ci.yml:129-134`, `ci.yml:240-245`).
- **A publish is all-or-nothing.** The per-architecture images are pushed untagged by digest; the tags exist only once `docker buildx imagetools create` has merged both, and the next step fails the run unless the list holds exactly `linux/amd64` and `linux/arm64`. No attestations or SBOM entries are built, so a list has two entries (spec 012 AC-2.1, AC-2.3, FR-1, NFR Reliability; `ci.yml:250-255`, `ci.yml:257-261`).
- **Every image carries the OCI labels** `source`, `version`, `revision`, `licenses` (`AGPL-3.0`) and `description`, the last two set by the workflow rather than the repository's settings (spec 012 AC-3.5, FR-2; ADR 0009; `ci.yml:135-137`, `ci.yml:246-248`).
- **Architectures are built natively**: `linux/amd64` on `ubuntu-latest`, `linux/arm64` on `ubuntu-24.04-arm`; the `-j 1` bootsnap precompile stays in the `Dockerfile` for local builds under emulation (spec 012 FR-3; ADR 0010; `ci.yml:95-100`, `Dockerfile:44`, `Dockerfile:57`).
- **Dependabot covers gems and GitHub Actions**, not the base image (spec 001 AC-2.6, FR-4; spec 012 Non-Goals; `.github/dependabot.yml`). Its version updates cover the dependencies a manifest names, so a gem that only another gem needs is never offered one, and a new release also waits out Dependabot's default 3-day cooldown and the weekly run (spec 036 Problem Statement; Dependabot's `allow` and `cooldown` documentation). On 2026-11-03 that left addressable, loofah, nokogiri and rails-html-sanitizer without a pull request while their advisories failed `bin/bundler-audit` on every pull request.
- **The Ruby gems' security updates are one group.** `groups.security` in the `bundler` entry (`applies-to: security-updates`, `patterns: ["*"]`) makes advisories that land together arrive as one pull request, because a fix per gem can't pass `bin/bundler-audit` while the other advisories stand (spec 036 FR-1, AC-1.1, AC-1.2; Dependabot's `groups` documentation; #164). The repository's own "Grouped security updates" setting combines with it and isn't relied on. Why Dependabot's security updates opened nothing for the five gems of 2026-11-03 is not known; the maintainer owns that question (spec 036 Open Questions, Decision 4).
- **A daily workflow audits `main`.** `.github/workflows/advisory-audit.yml` runs `bin/bundler-audit check --update` and `bin/importmap audit`, the two security audits of `config/ci.rb` (the gem audit spelled `check --update`, so that it fetches the advisory database on every run), once a day and by hand, with `contents: read` and a 10-minute timeout. The second audit runs after the first fails but not after a failed setup, so one run lists both and a broken setup never reads as a pass (spec 036 FR-2, AC-2.1 to AC-2.5, AC-2.9, AC-2.11). So an advisory published against a locked gem turns a run red within a day, without a pull request or a push. `config/importmap.rb` pins no versioned package, so the importmap audit checks nothing today and no response to it is defined until one does (spec 036 AC-3.3). The notice is the failed run and GitHub's own notification, which goes to whoever created the workflow, last changed its cron or re-enabled it (GitHub's documentation), so the maintainer changes the cron in a commit of their own after the merge (spec 036 Decision 7, AC-2.10). The repository is public, so GitHub disables the schedule after 60 days without repository activity; the next pull request's `checks` still gate (spec 036 Error Scenarios).
- **A red audit is fixed by one pull request:** run `bin/bundler-audit`, update every flagged gem in one change with `bundle update --conservative <gems>`, run `bin/ci checks` and the suite, and open one pull request (spec 036 AC-3.2; the fix of 2026-11-03 was #162).
- **Every action in the workflows is pinned to a full commit SHA with its version in a trailing comment**, and Dependabot's `github-actions` updates keep the pins current; the `image` job logs in to GHCR only just before "Push by digest", so no other step runs with the token on disk (issue #132). A new `uses:` line is pinned the same way.
- **A released migration is never edited, deleted or renamed, and `bin/ci` fails when one is.** The guard is a `bin/ci` step (`ruby script/upgrade/guard.rb`) that compares every file in `db/migrate/` at the previous release's tag (the newest stable tag below the tag being built) with the working tree, and uses no container engine (spec 031 FR-8, AC-8.1, AC-8.2, AC-8.4; `config/ci.rb:28`, `script/upgrade/guard.rb`). A migration, table or column added to `main` can need `script/upgrade/seeds/next.rb` or an entry in `script/upgrade/expected_changes.yml` to follow it; the proof fails and says which (spec 031 decisions 4 and 6).
- **The `image` job proves an upgrade from the previous release before anything is pushed.** After `bin/backup-smoke` and before the push, on both architectures and on every event, `bin/upgrade-smoke auto collector:smoke` boots the previous release's published image by its exact version tag, seeds it through its own code, starts the build on the same volume with the same secret, and fails unless the database upgraded unattended, lost nothing and the app served the collection as it was; so a tag whose build can't upgrade publishes nothing (spec 031 decision 8, AC-7.1, FR-1, FR-3; `ci.yml:164-166`). The comparison is Ruby on the runner reading consolidated snapshots with SQLite directly, and only the listed expected changes pass a difference (spec 031 decision 5, FR-4).
- **The `image` job checks out the full history and the tags and sets `BUNDLE_WITHOUT` at job level**, because the proof resolves the previous release from the tags and runs a host Ruby set up by `ruby/setup-ruby` (`Set up Ruby for the upgrade proof`) without the development and test groups (spec 031 AC-8.5, decision 5; plan P10; `ci.yml:91-92`, `ci.yml:105`, `ci.yml:117-120`). The `checks` and `rspec` jobs check out the full history too: `checks` because it runs the guard, the shards so that `bin/setup` and specs such as the git sandbox's behave as in a local run. The aggregate `ci` job has no checkout (spec 035 decision 5, which supersedes in part spec 031 AC-8.5's and decision 2's "`ci` job"; `ci.yml:26`, `ci.yml:49`). Neither `checks` nor any shard pulls the previous release's image or needs a container engine (spec 031 AC-7.6, now for those jobs, spec 035 Supersedes; `spec/script/upgrade/files_spec.rb`). Each shard installs libvips and ImageMagick before `bin/ci`, and `checks` installs no apt package (spec 014 AC-2.3, kept; spec 035 decision 5; `ci.yml:56-69`). The install step first checks that the Ubuntu mirror resolves; if it doesn't, it points the runner at public resolvers (1.1.1.1, 8.8.8.8), and it fails in seconds if the mirror still doesn't resolve, rather than letting apt retry for about 13 minutes (#306).

### The image

- **The image carries only what it runs.** The build context leaves out `docs/`, `spikes/`, `spec/`, `script/`, `.claude/`, `CLAUDE.md`, `.githooks/`, `orca.yaml`, `.worktreeinclude`, a checkout's `vendor/ocr` and `vendor/bundle` (the gems `ruby/setup-ruby` installs in the image job before the push), `bin/ghcr-cleanup`, `bin/backup-smoke`, `bin/upgrade-smoke`, `lib/collector/ghcr_cleanup.rb`, the CI tooling (`bin/ci`, `config/ci.rb`, `lib/collector/ci_groups.rb`, `lib/collector/ci_shard.rb`, `lib/collector/push_scope.rb`, which nothing in the image runs and which are required by path, not autoloaded, `config/application.rb`), and the API documentation (`doc/`, `.yardoc/`, `.yardopts`, `bin/yard`; the site's link extension is under `script/`, which is already left out, and the gem is in the development group, which the image's bundle leaves out), besides the paths the Rails template excluded (`config/master.key`, `.env*`, `storage/`, `.kamal/`, `config/deploy*.yml`) (spec 012 FR-3, AC-6.1, AC-6.4; spec 013 FR-5; spec 030 FR-9; spec 031 FR-7; spec 035 plan, Global constraints; spec 054 Story 3; ADR 0027; #31; `.dockerignore`). The image is public, so its source is readable by anyone who pulls it ([ADR 0008](../adr/0008-public-images-from-the-private-repository.md)); nothing that must stay private may be in the build context (spec 012 NFR Security).
- **`bin/image-smoke` fails an image** that doesn't boot, doesn't serve the registration page, `/scanner` (redirecting a signed-out visitor), the OCR engine files or the sign-in page, whose `catalog:status[mtg]` or `collector:user[...]` task fails, whose Active Storage variant transformer isn't vips, whose `/rails/vendor` holds anything besides `.keep`, `javascript` and `ocr`, or that holds any of the development-only paths, secrets, `bin/ghcr-cleanup`, `lib/collector/ghcr_cleanup.rb`, `bin/backup-smoke`, `bin/upgrade-smoke`, `doc`, `.yardoc`, `.yardopts`, `bin/yard` or the CI tooling above (spec 012 AC-6.1–AC-6.4; spec 013 AC-5.2; spec 014 AC-1.1–AC-1.3; spec 031 FR-7; spec 035 plan, Global constraints; spec 054 AC-3.3; #31; `bin/image-smoke:69`). CI runs it on both architectures before anything is pushed (spec 012 AC-4.3; `ci.yml:153-154`).
- **The image holds libvips and ImageMagick**, sqlite3 and curl; `ruby-vips` is bundled with `require: false`, so the app boots without libvips and variants fail loudly in the smoke test, not in production (spec 014 Story 1; [ADR 0013](../adr/0013-active-storage-variants-with-vips.md); [ADR 0012](../adr/0012-decode-art-images-with-imagemagick.md); `Dockerfile:19`, `Dockerfile:53`).
- **The runtime is Thruster in front of Puma as uid 1000.** The OCR engine is fetched and checksum-verified during the build, and no database file or secret is baked in (spec 001 FR-5, NFR Security; spec 012 FR-3; `Dockerfile:50`, `Dockerfile:69-71`, `Dockerfile:85`).
- **A server start checks the volume, then prepares the database; a one-off command does neither.** `bin/docker-entrypoint` runs `bin/rails start:check` and then `bin/rails db:prepare` only when the command ends in `./bin/rails server` (the image's default command does, as does any command that ends so), so booting a new image on an existing volume migrates it and never recreates a database, while `backup:restore` and the other tasks run before any migration (spec 001 NFR Reliability; spec 030 decision 10; `bin/docker-entrypoint:6-9`). `start:check` (`Collector::StartCheck`, `lib/tasks/start.rake`) has no `:environment` prerequisite, so it initializes nothing and needs no secret, and it opens no database: it asks the file system whether a prices file or one of its sidecars is on the volume and a primary isn't, a primary being there only if it exists, following a symlink, and isn't empty. It reads the files' places from `Collector::Backup::Databases`, so a start and a restore look at the same files. On that state it prints three sentences on standard error (what it found, why it stops, what to do) and exits 1 before `db:prepare`, changing nothing; the entrypoint is a bash `-e` script, so the start stops there (spec 086 decisions 1, 2, 4, 5 and 7, FR-1 to FR-3, AC-1.1 to AC-1.8, AC-2.1 to AC-2.7; #375). The check has limits: a one-off command that connects to the primary through the application writes its first page, and the next start then passes (spec 086 Non-Goals); and a command with trailing flags, such as `./bin/rails server -p 3000`, gets neither the check nor `db:prepare`.
- **The image carries three build facts, given as build arguments** (`COLLECTOR_VERSION`, `COLLECTOR_REVISION`, `COLLECTOR_SOURCE_URL`) and set as environment variables at the end of the final stage, after every `COPY`, with empty defaults: the facts are declared last, so these values, which change with every commit, invalidate no earlier layer. CI passes the same three to both of the image job's builds (Build, and Push by digest), which share a cache scope, so the pushed image is the tested one. OCI labels are not the carrier, because a running container can't read its own labels, and a file written in the build is not either, because `.git` is not in the build context. `config/deploy*.yml` is unchanged and `compose.yaml` only has a comment (spec 084 decision 3, FR-3; `Dockerfile`, `ci.yml:160-163`, `ci.yml:202-205`).
- **What each build reports.** CI's revision is `github.sha` and its source address is `<server_url>/<repository>/tree/<sha>`, so a fork that builds through the workflow offers its own source; the version is `docker/metadata-action`'s `version` output, or `pr-N` on a pull request, where that output is empty (spec 084 decisions 4 and 5):

  | Build | Version | Revision | Source address |
  |---|---|---|---|
  | Tag `vX.Y.Z` | `X.Y.Z` | the tag's commit | the tree at that commit |
  | Tag `vX.Y.Z-<suffix>` | `X.Y.Z-<suffix>` | the tag's commit | the tree at that commit |
  | Push to `main` | `edge` | the commit | the tree at that commit |
  | Pull request (built, never published) | `pr-N` | GitHub's merge commit | the tree at that commit |
  | Development checkout | `development`, unless one is given | `HEAD`, read from git once at boot, unless one is given | the upstream repository, unless one is given |
  | Test environment, or an image built without the facts | unknown | none | the upstream repository |

  A development checkout links to the repository, not the commit, because its commit may not be pushed; a pull request's merge commit may stop resolving once the pull request closes, which is accepted because its image is never published. Each fact is taken on its own, and the test environment never runs git (spec 084 decision 4). The source address is given whole at build time and never built from parts, so a fork on any forge passes its own; it is not a runtime setting, because the source offered must match the code that runs. A container's environment can override the variables and the app reads what the process has, but nothing documents that as a setting (spec 084 decision 5).
- **An untrusted fact falls back and never breaks a page.** Each is stripped of surrounding whitespace first. A version must then be 1 to 64 characters of letters, digits, `.`, `+`, `-` and `_` (`VERSION_RULE`); a revision exactly 40 hexadecimal characters in either case, shown lowercased, so a 7-character SHA from `git rev-parse --short` fails it (`REVISION_RULE`); a source address an absolute `https` URI with a host. A fact that fails its rule is treated as not given, and a value with bytes that aren't valid UTF-8 is scrubbed first, so reading never raises (spec 084 decision 6; `lib/collector/build_facts.rb`).
- **One reader, read once.** `Collector::BuildFacts` reads the three variables, the Rails environment and, only in development and only for a revision not given, `git rev-parse HEAD`; `config/initializers/build_facts.rb` keeps the result in `Rails.configuration.x.build_facts` for the process, so a request runs no git, query or call. The footer and every spec that checks the line read it. Specs supply facts with `build_facts(...)` (`spec/support/build_facts.rb`), which takes raw values through the same cleaning, replaces the kept facts for one example and restores them after, never by changing the process environment, as `:public_catalog` does for `Catalog.public?`. The reader names no collectible (`spec/footer_core_spec.rb`) (spec 084 decision 10, FR-2, AC-2.10; `lib/collector/build_facts.rb`).
- **A hand-built image gets its facts from the documented build command, not from Compose or Kamal's configuration.** Compose never builds: it runs `COLLECTOR_IMAGE`, and the README's "Building from source" is the `docker build` with the three `--build-arg` flags. Kamal's own-registry path passes them under `builder: args:`, shown in the README with ERB-evaluated, quoted values. The stock `config/deploy.yml` deploys the published image with `--skip-push` and stays as it is. A bare `docker build` still builds a working image (spec 012 AC-1.4); its footer reads "unknown version" and `bin/image-smoke` fails it, so the gap is never silent. Not chosen: a `build:` section in `compose.yaml`, because the Compose path is the published image and a second way to build would need its own documentation and smoke test, and a `builder: args:` block in the stock file, because the stock path never builds (spec 084 decision 9; the `Dockerfile`'s and `compose.yaml`'s comments point to the README, AC-5.6).
- **`bin/image-smoke` also fails an image that doesn't report its build facts.** It reads `COLLECTOR_VERSION` and `COLLECTOR_REVISION` from the running container (`printenv`, nothing else of the environment), strips whitespace as the app does, and fails, naming the three build arguments, when either is empty or the revision isn't 40 hexadecimal characters; it then reads the sign-in page and fails unless the licence line reads "Collector <version> (<the revision's first 7 characters, lowercased>)". It captures each output first and tests it after, as the other checks do. Because CI passes the facts, a published image always has them (spec 084 decision 7, AC-3.3, AC-3.4; `bin/image-smoke`).
- **`bin/image-smoke` also reads the third-party licences page.** The first-run check requests `/licences` beside `/registration/new` and fails unless it answers 200 before any user exists; after the build-facts check it requests the page once, captures it, and fails unless it holds "Third-party licences", the `tesseract.js` and `turbo-rails` rows (as `c-licences__name">NAME<`) and a gem's licence file under its own name (`c-licences__file">MIT-LICENSE<`, which only a gem's directory supplies, not the manifest), and fails if it lists `yard`, a `development` gem the image leaves out; the sign-in page it already reads must hold `href="/licences"`. So the page is proved on the image's own bundle, engine and files, not the repository's, which the guard spec in the suite covers as a superset. No `Dockerfile` or workflow change is involved: the manifest and its texts are in `config/`, which the image keeps (`.dockerignore` leaves out only `docs/`) (spec 087 decision 3, AC-1.3, AC-6.1, AC-6.2; `bin/image-smoke`; [catalog core](catalog-core.md)).

### Deployment

- **Compose runs the published image by default** (`image: ${COLLECTOR_IMAGE:-ghcr.io/plainprogrammer/collector:latest}`, no `build:`), refuses to start without `SECRET_KEY_BASE`, mounts `collector_storage` at `/rails/storage`, sets `SOLID_QUEUE_IN_PUMA`, and has a healthcheck on `/up`. It works with `docker compose` and `podman compose` (spec 001 FR-5, AC-3.5; spec 012 FR-4, AC-1.2–AC-1.5; `compose.yaml`).
- **Kamal deploys a release by version, without building:** `bin/kamal deploy --skip-push --version X.Y.Z` (`bin/kamal setup` the first time). The registry is `ghcr.io`, the image `plainprogrammer/collector`, the password `KAMAL_REGISTRY_PASSWORD`; Kamal needs credentials even to pull a public image. Never run a plain `bin/kamal deploy` against the public image: it would push a single-architecture `latest` over the published one (spec 012 FR-5, AC-5.1–AC-5.4; ADR 0009 Consequences; `config/deploy.yml:1-7`, `config/deploy.yml:34-43`).
- **No real host, registry credential or secret is committed.** The server in `config/deploy.yml` is a placeholder, `.kamal/secrets` reads the password from `KAMAL_REGISTRY_PASSWORD` and the master key from `config/master.key`, and the master key and `.env*` are git-ignored (spec 001 FR-6, AC-4.3, NFR Security). The secrets file is off-limits to agents, so its content is not checked here.
- **The instance is one host and one volume.** The queue runs inside Puma on both paths, so there is no separate worker or database server, and the volume is local, never a network file system (spec 001 AC-3.4, AC-4.2; ADR 0016; `.claude/rules/sqlite-and-migrations.md`).
- **The README documents both paths together** and says to pull the image, not the code, to upgrade; a change to a deployment file keeps the README's Self-hosting section in step (spec 012 FR-6, AC-7.3; CLAUDE.md "Deploy").

### The request body limit

- **A request body over 40 MB is refused before it is kept, at every layer that receives it:** Puma (`http_content_length_limit 40_000_000`, every environment), Thruster in the published image (`MAX_REQUEST_BODY`, which is unlimited by default), and kamal-proxy in a Kamal deployment (`proxy.buffering.max_request_body`, which buffers up to 1 GB to disk by default). The import file itself is refused over 32 MB before parsing, so between 32 and 40 MB the collector sees the app's reason and past 40 MB a plain 413 (spec 025 decision 6, AC-3.4; `config/puma.rb:38`, `Dockerfile:78`, `config/deploy.yml:29-32`). A reverse proxy in front of an instance keeps its own limit at 40 MB or more (README, Upload limit).

### Cleaning up the registry

- **The cleanup never deletes a tagged version or a digest a tagged manifest list references**, whatever its age, and never part of an orphan unit; it deletes a unit's manifest lists before its children (spec 013 FR-1, AC-2.1–AC-2.3; ADR 0011).
- **It fails closed.** It deletes nothing, or nothing further, when the version list, a tagged version's manifest or a candidate's manifest can't be read, when a tagged version isn't a manifest list of exactly `linux/amd64` and `linux/arm64`, or when a candidate has an unknown media type; it stops at the first delete refused with a status other than 404; it exits non-zero before any request without a token; it never retries a delete in the same run (spec 013 FR-2, AC-3.1–AC-3.8).
- **After deleting, it checks every tag** (re-reads each tagged list by digest, re-applies the two-platform rule and fetches each child), and fails the run naming the tag and digest of a missing one (spec 013 AC-2.4).
- **It is a dry run unless given `--delete`.** A workflow started by hand is a dry run unless `dry_run` is unticked, and its job has `packages: read` only; the scheduled run deletes with `packages: write`. No third-party code holds delete rights on the public image, and the command is stdlib-only (spec 013 FR-3, FR-4, AC-4.2, NFR Security, Portability; ADR 0011; `.github/workflows/ghcr-cleanup.yml`).
- **It never runs on a push or pull request and never changes `ci.yml`** (spec 013 FR-4).

### The stored import upload

- **At most one stored file per account, at most 32 MB, for at most an hour.** It is stored only when the previewed file can be applied and has something to change, recorded as `application/json` whatever the browser declared, and created analyzed so that no analysis job is queued (spec 028 decisions 1, 8, 9, AC-5.1; ADR 0022; `app/models/import_upload.rb`).
- **There is one removal path.** Applying, refusing, replacing, expiring and deleting the account all go through `ImportUpload#remove!`, which releases the blob after the commit, file first and then the blob row, rescuing failures and logging the exception class only; the request still succeeds (spec 028 decision 9, AC-5.4; ADR 0022; `app/models/import_upload.rb:57-58`).
- **The sweep never lists or deletes paths on disk.** `ImportUpload::SweepJob` runs every 15 minutes in development and production (`config/recurring.yml`), removes expired uploads and orphan blobs older than `ORPHAN_GRACE`, rescuing and logging per item, so an orphan goes within 25 minutes of its creation. `storage/` also holds the databases and `storage/catalog/` (spec 028 decision 9, AC-5.4, AC-5.5; ADR 0022).
- **Active Storage's routes are gated app-wide.** Direct-upload creation and the disk service's upload `PUT` answer 404 until a feature needs them; every other route needs a sign-in, and one that reads a blob needs a blob the signed-in account owns, else 404 (that ownership rule is [tenancy and accounts](tenancy-and-accounts.md)'). Only original blobs are authorised; variants and previews are not served until the first image feature extends ownership (spec 028 decision 8, AC-1.11, AC-1.12; ADR 0022 Consequences; `config/initializers/active_storage_gate.rb`).

### Backup and restore

- **A backup is an online snapshot of the primary database and then of the prices database**, each `VACUUM INTO` in its own read transaction, so the app keeps answering and writers wait no longer than the database's 5-second busy timeout. The two snapshots are seconds apart, not one moment; nothing ties them, because no key crosses the files (spec 081 decision 7, AC-4.8). A backup refuses an instance with no prices database: start Collector once on the release, which creates it (spec 081 AC-4.4). The databases a backup holds are `Collector::Backup::HELD` (spec 081 decision 6). The queue, cache and cable databases, `storage/catalog/` downloads, art images and index, Active Storage files and every secret stay out of it (spec 030 decisions 1, 2, 3, AC-1.2, AC-1.3, AC-4.1; ADR 0024 decisions 1 and 2; ADR 0016).
- **The destination is the operator's choice, never under `storage/`.** The commands take it as an argument and add no setting (spec 030 decision 4, hosted-door rule 3).
- **A backup is verified before it counts.** Each snapshot's integrity check and foreign-key check pass (the foreign-key count counts each violation of a `WITHOUT ROWID` table on its own, because SQLite names no row of one; spec 081 decision 3) and the archive reads back; otherwise no file has a final name and the run's `.partial` files are removed, with a plain message (spec 030 decision 7, AC-1.5, AC-1.12). The temporary files are created 0600 and the archive is `fsync`ed before it is given its final name; a final name is never replaced, because the archive is hard-linked into place (a rename only where a share can't link) (spec 030 decision 7, AC-1.6, AC-1.8, AC-1.9; ADR 0024 decision 3; `Collector::Backup.publish` in `lib/collector/backup.rb`).
- **A restore needs a fresh volume and never overwrites.** It refuses a volume that holds any of the five databases or a `-wal`, `-shm` or `-journal` file, with no override; it checks the file's kind, format version, checksums, each snapshot's integrity and foreign-key checks and schema before it places anything, and links the snapshots into place only after every check passes (spec 030 decisions 6, 10, AC-2.5, AC-2.6, AC-3.1–AC-3.7; spec 081 decision 8, AC-5.3 to AC-5.5).
- **A restore brings both databases back, or neither.** It places the prices snapshot first and the primary last; if the primary can't be placed, it removes the prices file it placed. A version 1 backup places the primary only, and the first start creates an empty prices database (spec 081 decisions 6 and 8, AC-5.1, AC-5.2, AC-5.6).
- **A killed restore can leave the prices file alone, never a primary without its prices.** The next restore refuses that volume, saying the file may be a stopped restore's, to remove it and its sidecars and restore again, and that Collector refuses to start on the volume as it is; and a server start does refuse it, before `db:prepare`, with the message above: a start would otherwise create a blank primary and keep the stale prices, which the new catalog's ids would attach to the wrong printings. The way out is to remove the prices file and its `-wal`, `-shm` and `-journal` files, then restore again onto a volume that holds no other Collector database, or start blank (spec 081 decision 8, AC-5.9; spec 086 FR-3, FR-4, AC-3.1; #375).
- **A restore never opens a connection to the primary's or the prices database's configured path** (that would create an empty file the next `db:prepare` takes for a blank instance, whose first visitor becomes admin), opens snapshots with `SQLite3::Database` and never Active Record (which would convert them to WAL), and runs no migration, `db:schema:load`, `db:reset` or `db:drop`; the first start's `db:prepare` migrates an older backup (spec 030 decisions 6, 10, FR-8, AC-3.6; ADR 0024 decisions 4 and 5).
- **A restore ends every session**: it clears `sessions`, which cascades to bulk removals and selections. Everyone signs in again; no collection is lost (spec 030 decision 3, AC-2.1, AC-2.4).
- **A backup restores onto the same release or a newer one.** A snapshot that lists a migration the release doesn't have is refused, naming both schema versions; the prices snapshot is checked against `db/prices_migrate/` and its refusal names the prices schema versions (spec 030 decision 10, AC-3.5; spec 081 AC-5.4). A release restores every backup format version it has shipped (`FORMAT_VERSIONS`), and refuses a newer one as unknown (spec 081 AC-5.7).
- **No secret is written, printed or logged**, and neither command prints account, email or lot data, only counts of accounts, users and lots, and of current prices and price changes (spec 030 decision 3, FR-10, AC-1.7, AC-1.8; spec 081 AC-4.7).
- **No page, route or admin action creates, lists, downloads or restores a backup**; the commands run in the operator's shell (spec 030 Non-Goals, AC-6.2; hosted-door rule 2).
- **The two tasks boot nothing.** They don't depend on `:environment`, so no initializer, queue or cache connection or `secret_key_base` is needed, and `lib/collector/backup/` is required by path, not autoloaded. It names no collectible (spec 030 FR-5; ADR 0024 decision 5; `lib/tasks/backup.rake`, `config/application.rb`).
- **A database beyond the five, a change to `Collector::Backup::HELD` that the guard's lists don't share, or a model with a collector-owned attachment other than `ImportUpload`, fails the suite** until the backup's contents are decided (spec 030 decision 2, AC-5.5; spec 081 AC-6.1; `spec/backup_guards_spec.rb`).

Its three safety warnings keep their meaning and prominence: the first person to reach an instance becomes its admin; signing in over plain HTTP; never run a plain `bin/kamal deploy` against the published registry (spec 020 AC-3.8, NFR Security).

## States and transitions

### A workflow run (`ci.yml`)

On every trigger that runs the workflow, `checks` and the `rspec` shards run in parallel and the aggregate `ci` job gathers them; the `image` jobs start only when `ci` has passed (spec 035 decision 5, AC-2.1, AC-3.7). M is the length of the `rspec` matrix, 4 at present (spec 035 decision 7; `ci.yml:44`).

| Trigger | `checks` | `rspec` (M shards) | `ci` | `image` (per architecture) | `publish` | Registry afterwards |
|---|---|---|---|---|---|---|
| Pull request | `bin/ci checks` | `bin/ci rspec N/M` | passes only if `checks` and every shard passed | build, `bin/image-smoke`, `bin/backup-smoke`, `bin/upgrade-smoke`; no login, no push | skipped | unchanged (spec 012 AC-4.2) |
| Push to `main` | `bin/ci checks` | `bin/ci rspec N/M` | same | same, then push by digest, untagged | merge digests into `edge` and `sha-<7>`, check two platforms | `edge`, `sha-*`; `latest` unchanged (spec 012 AC-4.1) |
| Tag `vX.Y.Z` | `bin/ci checks` | `bin/ci rspec N/M` | same | same | merge into `X.Y.Z`, `X.Y`, `latest`, and `X` from X ≥ 1; check | those tags (spec 012 AC-3.1, AC-3.2; ADR 0009) |
| Tag `vX.Y.Z-<suffix>` | `bin/ci checks` | `bin/ci rspec N/M` | same | same | merge into `X.Y.Z-<suffix>` | that tag only (ADR 0009; see the open note on spec 012 AC-3.3) |
| Any other tag | does not run | | | | | unchanged (spec 012 AC-3.6) |

A failure at any stage stops the later ones. A failing check or shard fails `ci`, while the other shards run to the end; if `ci` fails no `image` job runs and nothing is pushed, and a cancelled run doesn't run `ci` at all (spec 035 decision 5, AC-2.2, Error Scenarios); if one architecture's `image` job fails, `publish` doesn't run, so no tag exists for the run and an untagged digest from the other architecture may remain, for the cleanup (spec 012 AC-2.3, AC-3.4, Error Scenarios). The OCR engine download failing in the build fails the job; re-running retries (spec 012 Error Scenarios).

**Re-runs.** Only the newest release's workflow may be re-run: it builds a fresh two-architecture list from the same commit under the same tags (labels `version` and `revision` unchanged, layers not necessarily byte-identical), which is also how `latest` is restored if a plain `bin/kamal deploy` overwrote it. Re-running an older release moves `latest`, `X` and `X.Y` back to it (spec 012 AC-3.7, Error Scenarios; `docs/releasing.md`).

### A package version (GHCR)

| State | Meaning | Becomes |
|---|---|---|
| Untagged, fresh | a per-architecture image pushed by digest, or the previous list after a re-run, within the grace period | referenced once `publish` tags a list that names it; otherwise orphaned |
| Tagged | carries a tag (`latest`, `X.Y.Z`, `X.Y`, `X`, `edge`, `sha-*`) | never deleted by the cleanup |
| Referenced | untagged, but a tagged list names it as a child | stays, whatever its age |
| Orphan unit, young | untagged, unreferenced, newest member 7 days old or less | deleted when its newest member is strictly more than 7 days old |
| Deleted | removed by the cleanup, lists before children | |

(Spec 013 Terms, Story 1, Story 2.) A run proceeds: read every page of the version list; read the manifest of every tagged version and of every candidate; form the units; select those past the grace period; delete (in a deleting run); re-check every tag. On 2026-10-08 the package had 18 versions, 13 untagged, of which 10 were children of the five tagged lists and only 3 safe to delete, which is why "delete untagged versions" is wrong as a rule (spec 013 Problem Statement; ADR 0011). A run prints each selected version with digest, creation time and reason, and four disjoint counts (tagged, referenced, too young, selected) that sum to the number of versions (spec 013 AC-4.1).

### A stored import upload

Stored by a preview that can be applied and has something to change (a second preview replaces it; a preview that stores nothing leaves it), then removed when applied, refused at the apply, replaced, expired (an hour after it was stored) or when its account is deleted. An apply that fails or is refused for a changed plan or an unconfirmed removal leaves it until it expires. An expired upload is never applied, whatever the sweep's timing: the apply judges expiry once, inside its write transaction (spec 028 decision 9, AC-3.3, AC-5.1, AC-5.2, AC-5.6; ADR 0022). A backup holds the `import_uploads` row but not the file; after a restore an apply answers 422 "Preview the file again." and the sweep removes the row once it has expired (spec 030 AC-2.10).

### A backup run (`backup:create`)

1. Refuse, writing nothing, if the destination doesn't exist, isn't writable by the container's user, the prices database is missing, or the destination has less free space than twice the two databases' sizes together (spec 030 AC-1.11; spec 081 AC-4.4, AC-4.6).
2. Remove `.partial` files of its own name pattern older than a day (spec 030 AC-1.6, FR-6).
3. `VACUUM INTO` a snapshot of the primary under a random `.partial` name, 0600, then one of the prices database; put each in rollback-journal mode; verify each one's integrity and foreign keys; write the manifest (format version 2) and the archive under a `.partial` name; read the archive back; link it to `collector-backup-<UTC>.tar.gz`; `fsync` the directory (spec 030 decisions 5 and 7, AC-1.1, AC-1.4; `lib/collector/backup/create.rb`).
4. On any failure remove the run's own `.partial` files and exit non-zero with a plain message. A damaged database and an orphan row (a foreign-key violation) each get their own message, naming the prices database when it is the one; the orphan message points to each collector's export (spec 030 AC-1.5, AC-1.12; spec 081 AC-4.5). A name already taken fails the run and leaves the existing file untouched (spec 030 AC-1.9).

### A restore run (`backup:restore`)

Checks, in this order, before anything is written on the volume other than the temporary files (`collector-restore.partial` and, for version 2, `collector-restore-prices.partial`) and their `-journal`s: the volume is fresh (spec 030 AC-2.5); the file's kind (not a backup; or incomplete, being cut short, failing its gzip check or named `*.partial`) (AC-3.1, AC-3.3); the backup format version is one this release restores (AC-3.4); the volume has room for both snapshots; the checksums (AC-3.2); each snapshot's integrity and foreign keys (AC-3.7); each schema is not newer than the release's (AC-3.5). Then every session is ended in the primary, the counts of both are compared with the manifest, and the snapshots, closed in rollback-journal mode, are `fsync`ed and linked to their paths, prices first and the primary last, never replacing a file (spec 030 FR-2, decision 6; ADR 0024 decision 4; spec 081 decision 8). Every refusal exits non-zero, names what is wrong and what to do, and leaves the volume as it was; a restore stopped after the temporary files are written leaves no database, and the next restore removes the leftovers (spec 030 AC-2.6, AC-3.8, FR-4; spec 081 AC-5.6). For a killed run between the two placings, see the invariants above (AC-5.9). The report gives both sets of counts and both schema versions; for a version 1 backup it says the backup holds no prices and that the first start creates an empty prices database (spec 081 AC-5.1, AC-5.2). The closing message says to start the instance, that everyone signs in again, that pending bulk-removal Undos and selections are gone, and that the art index is rebuilt with **Build art index**; a backup with no users says the first person to reach the instance becomes its admin (spec 030 AC-2.1, AC-2.11).

**Restoring onto an instance.** The restore runs as a one-off container against the empty volume, before the first start, as uid 1000, with the file placed where uid 1000 can read it (a host directory owned by 1000 and mounted read-only, or created and copied in, then `chown`ed by a one-off as root). Under Kamal the sequence is `kamal server bootstrap`, a one-off `docker run` of the exact release over `ssh`, then `kamal setup` or `deploy` for that version (spec 030 decision 4; README, "Restore").

### An upgrade

A new release reaches an instance by `docker compose pull && docker compose up -d` or `bin/kamal deploy --skip-push --version X.Y.Z`; the container's start runs `db:prepare`, which migrates the volume's databases unattended. `docs/releasing.md` lists, newest first, the upgrade notes an operator needs for each release (spec 001 NFR Reliability; spec 012 AC-1.3, AC-5.2; `docs/releasing.md`).

CI proves one release step of it: the previous release's published image, seeded through its own code, upgraded unattended by the build on the same volume, nothing lost and the app serving the collection as it was; and, once the previous release has `backup:create`, a backup it took restores onto the build and is judged the same way (spec 031 decisions 1, 4, 7). The proof covers the prices database too: the upgraded and the restored volumes must hold `production_prices.sqlite3` with every version of `db/prices_migrate/`, sound, its two large tables `WITHOUT ROWID`; when the previous release's tag has `db/prices_migrate/` (decided from the tag, not from the volume), its prices database is compared with the upgraded and the restored ones by the primary's rule; the next seed fills the prices tables and the coverage rule reaches them. Expected changes and seed exceptions are split between the two databases by the prices tables (`db/prices_structure.sql`), so an entry for no table is still reported; an expected change may name a migration of `db/prices_migrate/`, and the migration guard reads that directory too (spec 081 decision 10, AC-6.4 to AC-6.8; it supersedes in part spec 031 AC-2.1, AC-2.4, AC-2.5, AC-3.2, AC-4.5, AC-6.2 and AC-8.1, whose frozen `contracts/yaml-files.md` still says `db/migrate/` only). Its limits: one step only, from the newest stable tag below the tag being built, never a chain from older releases; the old database is a seeded one, not a real instance's data (spec 031 Non-Goals; see Accepted limits).

The proof stops each instance it boots and compares databases (the previous release's, the upgraded one, the restored one, the next seed's) only after a graceful stop, a status of 0 or 143. It stops an instance only once Solid Queue's dispatcher, worker and scheduler have each logged `Started`, reading the log up to 15 times 2 s apart; an instance whose queue doesn't start that way fails the proof, naming what is missing and quoting its last 20 log lines, as spec 031 FR-5 allows no warning that lets the job pass. Why: Solid Queue's Puma plugin forks its supervisor when Puma has booted and, on a stop, sends it INT and waits for it without a bound. A stop that arrives before the supervisor has trapped signals is swallowed, so Puma waits until the engine kills the container at the end of the grace period (exit 137); a stop that arrives while the supervisor's three processes are still starting has its TERM lost to them and takes the supervisor's 5 s `shutdown_timeout` instead. The proof used to stop an instance at its first `/up` answer, which lands in those windows by chance, more often on a slow runner (#177: exit 137 on `Image (linux/amd64)` in runs 42131733342, 42124366255 and 42658829910). A stop that is not graceful fails with how long it took and the container's last 20 log lines (#177). Only the proof stops an instance gracefully: `bin/image-smoke` and `bin/backup-smoke` remove their containers, so they need no wait.

## Decisions not in an ADR

- **Releases are cut by tagging, and the checks around the tag are procedure.** The workflow publishes on any matching tag; that the tag is annotated and on `main`, that `main` is green, and the two pre-announcement checks (restore the maintainer's own export for a release touching import or export, restore the maintainer's own backup for a release changing the schema, the backup or the restore) are steps in `docs/releasing.md` (spec 012 AC-7.1; spec 028 AC-6.5; spec 030 AC-5.7, decision 14). Around the upgrade proof the procedure adds three steps: before the tag, the seed `next.rb` is renamed to the version being cut and the `next` key of `seed_exceptions.yml` is renamed with it (`docs/releasing.md` step 1); after the tag is pushed, the `Upgrade smoke test` step of both `Image` jobs is read, and a failed tag is never moved, reused or deleted (step 3); and after the tag, the expected changes whose migration the tag contains are deleted (step 7) (spec 031 decision 9, AC-9.1).
- **Going public is manual and ordered** (push the first image, verify an authenticated pull, link the package, change visibility, verify an anonymous pull), because the change cannot be undone; the workflow never does it. ADR 0008 records the decision; the steps are `docs/releasing.md`'s "Going public (one time)" (spec 012 AC-7.2, Error Scenarios). The package is public now (a pull of `edge` and the tags works anonymously, spec 013 AC-2.5 and its `verification.md`).
- **The cleanup's token.** The workflow's own `GITHUB_TOKEN` deleted versions on the first deleting run (2026-10-18). `docs/releasing.md` still documents the fallback (a classic personal access token with `read:packages` and `delete:packages` as `GHCR_CLEANUP_TOKEN`; GitHub Packages accepts no fine-grained token), because GitHub documents token deletion as a public preview (spec 013 Open Questions, AC-2.5; `verification.md` "Live cleanup").
- **A failed cleanup run failed closed.** It is investigated before it is re-run, and versions are never deleted by hand to get past it (spec 013 AC-5.1; `docs/releasing.md`).
- **Backups are the operator's, not the app's.** There is no scheduler, retention, off-site upload or page; the documents show a cron line and a Kamal alias. Litestream, a stopped-volume copy and host volume snapshots are named as alternatives the app doesn't test (spec 030 decisions 1 and 8; ADR 0024).
- **The Kamal restore path is documented, and its container command is tested, but it isn't exercised through Kamal itself** (the maintainer has no Kamal host). The `backup` alias and the commented backup-directory volume in `config/deploy.yml` are the stated additions; the volume line stays commented because Docker creates a missing bind-mount source owned by root, which uid 1000 can't write to (spec 030 decision 4; `config/deploy.yml:94-103`).
- **`bin/backup-smoke` runs in the image job, after `bin/image-smoke`, on both architectures, and is not a `bin/ci` step** because it needs a container engine, as `bin/image-smoke` does. It takes an optional second image to restore into, which the upgrade proof does not use: its backup leg is in `bin/upgrade-smoke`, which restores the backup of its own seed (spec 030 decision 9, AC-5.2, AC-5.3; spec 031 decision 7; plan P3; `ci.yml:158-159`). It seeds a price row in the first container (through `PricesRecord`, so that container's prices database must exist), and fails unless each restored container's volume holds the five databases and the price row, and the restore's report gives the prices counts (spec 081 decision 10, AC-6.3). A last leg restores into a fourth volume, removes the primary (the state a killed restore leaves) and runs the image detached on it with its default command, waiting a bounded time: the container must stop with status 1 and its log carry the message, the volume must hold no primary, and after the prices files are removed a start must be a blank instance with the five databases (spec 086 AC-4.1, AC-4.2; the wait is bounded so an image that doesn't refuse fails the leg and names the spec, instead of hanging).
- **The smoke scripts capture a command's output first and test it after; they never pipe into a reader that exits early** (`| grep -q`, `| grep -m`, `| head`) under `pipefail`. Once such a reader has matched and gone, the writer's next write fails (curl exits 23) and `pipefail` fails the check although the page held what was looked for; with GNU grep, as on the runners, a page shaped like the restored `/collection` (13,516 bytes) delivered in two writes 5 ms apart failed 100 of 100 times at a 13,000-byte split (2 of 100 at 12,000), and that page does reach curl in varying pieces (one, two or three receives, measured against the same instance). `spec/smoke_scripts_spec.rb` sweeps `bin/backup-smoke`, `bin/image-smoke` and `bin/upgrade-smoke` for such a pipe. When `bin/backup-smoke`'s check of the restored collection page fails it prints the status, the byte count, the redirect target, whether the cookie jar holds the sign-in's `session_id` cookie and the first 300 bytes of the body, and a failed sign-in prints its status (#217; `bin/backup-smoke`, `collection_has_lot`).
- **The previous release is the newest stable tag below the tag being built** (`auto`; a pre-release is never one, and the first release has none, so the proof passes with a notice that says so), and its image is pulled by that exact version tag, never `latest`, `edge` or a `sha-` tag (spec 031 decision 2, FR-1, AC-1.3; plan P2).
- **The backup leg's allowance is the four tables the restore empties.** Restoring the previous release's backup is judged as the upgrade is, except for the tables `backup:restore` clears (`sessions`, `bulk_removals`, `bulk_selections` and `bulk_selection_marks`, `Upgrade::ExpectedChanges::RESTORE_ENDS_SESSIONS`), which are expected to differ (spec 031 1.1.2, decision 7; spec 030 decision 3).
- **The seed fills the catalog directly and never exercises a refresh**, so the Monday 03:15 refresh window is outside the proof (spec 031 decision 4).
- **A restore deletes only its own temporary file and the `sessions` rows (and their cascade)**; the freshness test ignores that temporary file by name (spec 030 FR-6).
- **An archive is hard-linked into place** where spec 030 decision 7 says it is renamed: the code and ADR 0024 decision 3 link it (so a clash is detected and an existing file never replaced) and fall back to a rename only where a share can't link, after checking that the name is free. The same holds for the restore's placing of the snapshot (ADR 0024 decisions 3 and 4; `Collector::Backup.publish` in `lib/collector/backup.rb`, `Restore#call` in `lib/collector/backup/restore.rb`). ADR 0024 is the source for the current behaviour.
- **Specs 001's Compose and Kamal parts were changed by spec 012**: Compose runs the published image instead of building (`build: .`), and Kamal's placeholder registry became `ghcr.io` with credentials active. Spec 001 isn't edited; the area doc is right where they differ (spec 012 FR-4, FR-5; spec 027 D4).
- **The README's introduction and sections are checked by hand, not by RSpec**, and a spec that checks a prose document is without precedent for the maintainer (spec 020 decisions 3 and 7).

- Active Storage use for global (non-account) records, and serving variants or previews, stay blocked until an ADR or the first image feature changes the gate (ADR 0022 Consequences).
- A backup's read transaction holds the WAL back for its length (up to 5 minutes at the bar), so the `-wal` file grows with the writes of those minutes; there is no restore over a live instance, of one account, or onto an older release, and no point-in-time recovery (spec 030 decision 13, Non-Goals; ADR 0024 Consequences).
- A restore onto the wrong volume (a Compose project name that differs from the instance's) restores into that volume and prints its path and counts; the operator compares them before starting, because an instance started on a different, empty volume is blank and open to the first visitor (spec 030 Error Scenarios).
- **A stop within about 1–2 s of the app becoming ready can hang until the engine's grace period and be killed.** The window opens when Puma has booted (after `db:prepare` and Rails' boot, so later than the container's start) and closes when Solid Queue's supervisor and its three processes have trapped signals, which takes longer on a slow host. It is Solid Queue's Puma plugin (gem 1.7.0; 1.7.2 doesn't change it), not Collector's code: an instance stopped in it is killed at the end of the grace period (exit 137; 10 s by default under `docker compose stop`, 30 s under the proof), and one stopped while the three processes start takes up to the supervisor's 5 s `shutdown_timeout` more, which on a starved host can pass the 10 s default. No committed write is lost: SQLite's write-ahead log recovers on the next boot, and a killed process is not a power loss. A job a worker was running at that moment is released or failed by Solid Queue's pruning and can be retried at `/admin/jobs`. A stop once the three processes have logged `Started` is graceful (45 of 45 local stops that waited for them: 30 at full speed in 0.4–0.9 s, 15 on 0.3 CPU in 1.9–6.5 s). The maintainer ruled it a known limit: no app-side fix and nothing filed upstream (#177). The upgrade proof avoids it by waiting (see An upgrade).
- **The upgrade proof covers one release step.** No chain from older releases is tested; the old database is the previous release's own schema loaded by its own code and filled by a seed, not a real instance's data, so the hand restore of the maintainer's real backup (spec 030 AC-5.6; `docs/releasing.md` step 5) stays manual; and the deliberately failing tag that shows a failed proof publishes nothing (spec 031 AC-7.2) is the maintainer's check, recorded in spec 031's `verification.md` (spec 031 Non-Goals, decisions 1, 4, 9).
- The first deleting cleanup run and the NAS restore of spec 030 (AC-5.6) are the maintainer's checks, recorded in `verification.md` of specs 013 and 030.
- **#217's trigger on the arm64 runner was not reproduced.** `bin/backup-smoke`'s "the lot isn't on the collection page" failed three times on `Image (linux/arm64)` (two of the last ~11 `main` runs and a pull request), amd64 green on the same commits; the pipe above is the one mechanism shown to produce it (the split-write trials), and the scripts no longer have it, but 20 clean local runs and about 3,800 trials against the real restored instance never failed before the change either, so the issue closes only after green arm64 image jobs on `main`. If the check fails again, its diagnostics say whether the page was a redirect, an error or the page without the lot (#217).
- **Four shards won by one second.** Decision 7's stop rule kept M = 4 on a 31 s margin against its 30 s threshold, inside the tens of seconds GitHub's job times vary by; a later trial may land on 3. A stale run-time log changes only the shards' balance, never which files run (spec 035 AC-2.5, NFR Performance).
