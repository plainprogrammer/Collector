# Catalog operations

How the catalog changes, and how admins start, watch and recover that work: the catalog refresh, the MTG art index build, their rate-limit retries, the admin catalog page (`/admin/catalog`) and the jobs pages (`/admin/jobs`). This is the current truth; the specs it distils record what each feature promised when it shipped (see Sources and the [specs index](../specs/README.md)).

## Scope

**Covers:**

- The refresh's run and its lifecycle: `Catalog::Refresh`, `Catalog::RefreshRun`, `Catalog::Refresh::Progress`, `Catalog::RefreshJob`, the weekly schedule (`config/recurring.yml`, which also schedules the import upload sweep, `ImportUpload::SweepJob`, every 15 minutes in development and production, spec 028 AC-5.5, [ADR 0022](../adr/0022-stored-import-upload-retention.md); it shows on `/admin/jobs` like any job), the `catalog:refresh` and `catalog:status` tasks (`lib/tasks/catalog.rake`), and the source contract's optional hooks (`app/models/catalog/sources.rb`).
- What a source does for a refresh, for the one source so far: `MTG::Scryfall::Source` (the bulk file, its check, kept downloads, the language setting) and the waits and timeouts of `MTG::Scryfall::Client`.
- Rate limits: `Catalog::RateLimitRetry`.
- The art index build's run and lifecycle: `MTG::Art::BuildJob`, `MTG::Art::Build`, `MTG::ArtBuild`, `MTG::Art.after_refresh`, `MTG::Art.status_line`, and `MTG::Art::Decoder` as far as a missing ImageMagick fails a build.
- The admin pages: `Admin::CatalogsController`, `Admin::Catalogs::OperationStartsController`, `Admin::Catalogs::OperationRetriesController`, `Catalog::Health`, `Catalog::Operation` and `Catalog::Operation::Queue`, `Catalog::RefreshOperation`, `MTG::Art::Operation`, `Catalog::FailureReason`, `AdminHelper`; `Admin::JobsController`, `Admin::Jobs::RetriesController`, `Admin::Jobs::DiscardsController`, `BackgroundJobs::List`, `BackgroundJobs::Entry`; the `poll` Stimulus controller; the not-loaded notice (`app/views/catalog/_not_loaded.html.erb`).

**Neighbours:**

- The catalog's own records (entries, sets, identities and their extension tables), the name index a refresh rebuilds, how a source record is mapped, the source contract's data records, and catalog search are **[catalog core](catalog-core.md)** (spec 002 FR-1, FR-2, FR-7–FR-10). Which rows a refresh writes, and when, is here (spec 002 FR-4).
- What the artwork table holds, the fingerprint, which image an artwork uses, the index file's format, serving it and matching in the browser are **[scanner](scanner.md)** (spec 011 apart from FR-2's build run; ADRs 0006, 0007, 0012).
- The admin flag and the `AdminOnly` guard are **[tenancy and accounts](tenancy-and-accounts.md)** (spec 004).
- Running Solid Queue inside Puma (`SOLID_QUEUE_IN_PUMA`) and the volume that holds `storage/catalog/` are in CLAUDE.md and **release and deploy**.
- The daily price refresh reads the file this refresh's source downloads, through the same `#languages`, `#current_version` and `#download`, and is not a `Catalog::Operation`: its job, run record, guards and rules are in **[prices](prices.md)** (spec 089 decision 1). What the sharing means for the download is under "What the source does for a refresh" below.

## Glossary

- **Catalog type:** a kind of collectible with a registered source (`config/initializers/catalog.rb`, which registers `mtg` today) (spec 015 Glossary).
- **Operation:** something an admin can start for a catalog type and watch: the **refresh**, which every type has (`Catalog::RefreshOperation`), and any extra operation a source adds through its optional `.operations` hook (spec 015 FR-2). For `mtg` that is the **art index** build (`MTG::Art::Operation`).
- **Trigger:** how a refresh was asked for: `scheduled` (the weekly schedule) or `manual` (the rake task, "Refresh now", a console) (spec 002 FR-4; `Catalog::RefreshRun::TRIGGERS`).
- **Run:** one attempt of a refresh (`Catalog::RefreshRun`) or of an art build (`MTG::ArtBuild`), with its job id, status, counts and progress or heartbeat (spec 015 FR-1; spec 011 AC-3.2).
- **Loaded:** a catalog type with at least one applied refresh run (spec 015 Glossary; `Catalog::Health#loaded?`, `Catalog.unloaded_titles`).
- **In flight:** an operation with an unfinished job of its job class (for a refresh, queued for its type) in the queue (ready, blocked by a concurrency limit, scheduled including retry waits, or claimed), whoever queued it, or whose run is running and not left behind. A failed job is unfinished but not in flight (spec 015 Glossary; `Catalog::Operation#in_flight?`, `Catalog::Operation::Queue`).
- **Queued (operation state):** in flight with no running run yet, or with only a left-behind one (spec 015 Glossary, AC-3.2, AC-4.10).
- **Last progress / heartbeat:** a refresh run's last recorded progress (`heartbeat_at`, or `started_at` before any; `Catalog::RefreshRun#last_progress_at`), an art build's `heartbeat_at` (spec 015 FR-1; spec 011 AC-3.2).
- **Stalled:** running, last progress older than the stall threshold (`STALL_AFTER` for a refresh, `STALE_AFTER` for a build), and its own job still claimed by a worker. Shown as running or building, never as interrupted (spec 015 Glossary, AC-3.6, AC-4.11; #79).
- **Left behind / interrupted:** a run still marked running that nothing works on any more; see States and transitions for the rules. On the pages and in `catalog:status` it reads "interrupted", and a starting job closes it as failed with the message `interrupted` (spec 015 Glossary, AC-3.2, AC-3.3, AC-3.9, AC-4.10; #60, #73).
- **Waiting retry:** an unfinished job of the same operation (for a refresh, queued for the same type), other than the starting one, that the queue holds for a later time (spec 024 Problem Statement, decisions 3 and 5; `Catalog::Operation::Queue#waiting_to_retry?`). Retry now runs the failed run's own waiting job (spec 055).
- **Starting job:** the job whose `Catalog::Refresh#call` or `MTG::Art::Build#call` is running the start guard (spec 024 Problem Statement).
- **Ready (art index):** the latest build not skipped is finished and the index file it names (`MTG::ArtBuild#index_file`) is in `storage/catalog/mtg/art/index/`. The file is judged by its name only: `MTG::Art::Index.file?` accepts only a name of the index's own shape (`MTG::Art::Index::NAME`), makes one `stat` per panel render or status line, and never opens or caches the file. A blank or other-shaped name, an absent directory and a volume that can't be examined all read as missing (spec 039 decisions 1 and 4; #122). Ready also means the build was made at the current fingerprint settings (`MTG::ArtBuild#settings_drift?`): a build made with another `settings_digest` is **out of date**, which the scanner refuses, so it has its own state; a build for an older catalog version (`#catalog_drift?` against `MTG::Art.latest_catalog_version`, the latest applied refresh's `source_version`) is still ready, which the scanner keeps using, with a warning fact. A blank digest, a blank build version, or a latest applied refresh with no `source_version` isn't judged (spec 053 decision 1, Problem Statement; #176).
- **Stages of a refresh:** download, sync, retire, index, in that order, shown as "Download", "Sync cards", "Retire missing cards", "Rebuild name index" (`Catalog::RefreshRun::STAGES`, `Catalog::RefreshOperation::STAGES`; spec 015 Glossary).
- **Job states on the jobs pages:** Failed (failed, not retried or discarded), Running (claimed by a worker), Queued (ready, or blocked by a concurrency limit, marked "waiting"), Scheduled (due later, including retry waits); every job in every queue counts (spec 015 Glossary, AC-6.1, AC-6.2).
- **Admin / member:** a signed-in user with or without `admin` (spec 015 Glossary).

## Invariants

- **Catalog data changes only through jobs.** Catalog rows change only through `Catalog::Refresh`, which `Catalog::RefreshJob` runs (the weekly schedule, `bin/rails "catalog:refresh[<type>]"`, or "Refresh now") (spec 002 FR-3, FR-4; spec 015 FR-3). Artwork data, the art cache and the art index change only through `MTG::Art::BuildJob` (spec 011 FR-2). No request or page render calls a source (spec 002 FR-3 must-not; spec 015 FR-3 must-not). Nothing fetches an artwork image during a request, on boot, or with art matching off (spec 011 FR-1, FR-2 must-not).
- **Nothing queues a refresh by itself.** Only an admin's start request, the schedule and the rake task do; not boot, not sign-up (spec 015 AC-1.5, FR-6).
- **Starting from the page bypasses no guard.** A start request queues the operation's existing job (`Catalog::Operation#start`), never runs it in the request. "Refresh now" queues `Catalog::RefreshJob` with the `manual` trigger, as the rake task does, so it passes through `Catalog::RefreshRun.start!` (spec 015 FR-3, AC-2.15). "Build art index" queues `MTG::Art::BuildJob`, as the refresh does, so it passes through `MTG::ArtBuild.start!` (spec 015 FR-3).
- **The core never names a collectible.** The admin catalog page's core code (its controllers and views, `Catalog::Operation` and `Catalog::Operation::Queue`, `Catalog::RefreshOperation`, `Catalog::Health`, `Catalog::Refresh::Progress`, `Catalog::FailureReason`, the not-loaded notice, `AdminHelper` and the `poll` controller) contains no collectible's, source's or operation's name, checked over those 16 files by `spec/admin_catalog_core_spec.rb` (spec 015 AC-5.4, FR-2 must-not; ADR 0018). A source reaches the core only through optional hooks: `#progress=`, `#reapply?`, `#after_refresh`, `.title`, `.operations`, `.failure_reasons` and `.status_lines` (spec 015 FR-2; spec 011 AC-2.4, AC-3.11; #84). Elsewhere in `app/models/catalog/` and `app/jobs/catalog/` a collectible is named only in comments that give an example (spec 024 NFR "Core boundary"; see `verification.md`).
- **Two refreshes of one type never apply at once.** `Catalog::RefreshJob` holds a queue concurrency lock per type (`LOCK_FOR`), so a second job waits its turn, and `Catalog::RefreshRun.start!` records a new run as skipped while another is running and not left behind (spec 002 FR-4; spec 015 AC-2.15).
- **Two art builds never work at once.** `MTG::ArtBuild.start!` guards it on the run records and job ids, not on a queue lock, which a first build would outlast; `MTG::Art::BuildJob` has none (spec 011 AC-3.2; spec 024 decision 4).
- **The queue is read before the runs.** Every judgement of a run by its job reads Solid Queue's tables first (`Catalog::Operation::Queue#read`), and judges no run that started after that reading: a job's row is finished only after its run is closed, so a run whose job that reading no longer held was left behind, not finished between the two reads. `Catalog::Refresh#call` and `Catalog::RefreshOperation` read it first (spec 015 FR-1, AC-3.3; #60). So do `MTG::ArtBuild.start!`, `MTG::Art::Operation` and `MTG::Art.status_line` (spec 015 AC-4.10; #73).
- **No sooner than the source asked.** A job turned away by a rate limit runs again no sooner than the source asked, and no other job of its operation asks the source meanwhile (spec 002 FR-4; spec 011 AC-3.6; spec 024; #74, #78).
- **Progress is written outside the batch transactions** and never lengthens them; how often it is written depends on records seen and time, not on rows changed (spec 015 FR-1).
- **A refresh writes only what changed, and never deletes.** Entries, sets and identities are upserted by the source's stable key in batches of `Catalog::Refresh::BATCH_SIZE`, only when their content digest changed (or a retired entry came back); entries the source no longer lists are retired, and only after the whole file was processed; nothing is deleted and an entry keeps its internal id when updated or restored (spec 002 FR-4).
- **A retry or discard from the jobs pages changes no run** by itself; a retried job changes runs only when it runs (spec 015 AC-6.11).
- **Pages poll only while work is in flight**, with the `poll` controller, re-rendering from recorded state; jobs never broadcast or render (spec 015 FR-4; ADR 0015).
- **The jobs pages read Solid Queue's own tables** and retry or discard only failed jobs, through Solid Queue's own operations; a request names only a job's id, a catalog type and an operation's key, each looked up among what exists (spec 015 FR-5, FR-7; ADR 0014).
- **The catalog page moves one scheduled job, through the queue's own operations.** "Retry now" names only a type and an operation key, takes the job from the operation's own latest failed run, runs nothing in the request and writes no run record; it is admin only like the rest of the page (spec 055 decision 4, FR-1; ADR 0014). Moving the job keeps its Active Job id and its Active Job arguments as they were (spec 055 FR-2); the queue's own bookkeeping in the stored row may change, as Solid Queue 1.7.2 records there which concurrency semaphore the dispatched job took its slot from (maintainer ruling on [#283](https://github.com/plainprogrammer/Collector/issues/283)).
- **A failure is shown as a plain sentence, never an error's class name.** A failed run or build stores `"<error class>: <message>"`; `Catalog::FailureReason` derives the sentence from it each time it is shown, so runs that failed before #84 read the same way. The core words `Catalog::Sources`' errors and a busy database, a source words its own errors through `.failure_reasons`, and anything else reads "An unexpected error stopped it."; a message that isn't an error's (`interrupted`) is shown as a sentence. The panel keeps the stored text as a "Technical detail" fact; `catalog:status` and the log print the stored text unchanged (#84). `MTG::Scryfall::Source` words a missing ImageMagick this way (#84).
- **Admins only.** Every page and action of `/admin/catalog` and `/admin/jobs` answers 404 to a member (nothing is queued, retried or discarded) and sends a visitor to sign in (spec 015 FR-7, AC-7.1, AC-7.2).

## States and transitions

### Refresh run (`Catalog::RefreshRun`)

Statuses: `running`, `applied`, `skipped`, `failed`. Each attempt, a job system retry included, records its own run (spec 002 FR-4).

- **Start** (`Catalog::RefreshRun.start!`, inside one transaction, called by `Catalog::Refresh#call` with the queue it read first):
  1. Close as `failed`, message `interrupted`, each run of the type still marked running whose last progress is older than `STALL_AFTER` (whether or not a worker holds its job); or whose job id is the starting job's own (the queue re-ran it after a restart, or an admin retried it); or whose last progress is older than `JOB_ENDED_GRACE` and whose job is in the queue's failed list or held by no unfinished job in the queue as read (spec 015 AC-3.3; #60). A run started after the reading isn't judged by its "held by no job" part. A run whose job id is outside the queue (`Catalog::RefreshJob.perform_now` in a console) is judged the same way: once it goes `JOB_ENDED_GRACE` without progress it reads interrupted, and a refresh that starts closes it. A run that recorded no job id (a refresh started without a job, a run from before spec 015) is judged only by `STALL_AFTER` and never matches another by id (spec 015 AC-3.3, AC-3.4).
  2. If a run is still running, record the new run as `skipped` with `already running` (spec 015 AC-3.4; spec 024 AC-1.8). (Spec 002 FR-4 and its Error Scenarios rows "Process killed or deployed mid-refresh" and "Refresh triggered while one is already running" said a run younger than 6 hours blocked a new one; changed by spec 015 AC-3.3 and #60 to the rules above.)
  3. Otherwise, if a waiting retry of the type's refresh exists (`Catalog::Operation::Queue#waiting_to_retry?`, leaving out the starting job's own id), record the new run as `skipped` with `waiting for another job's retry` (`Catalog::RefreshRun::WAITING_FOR_RETRY`): it asks the source nothing and runs no `after_refresh` hook, and the waiting job does the work. Manual and scheduled refreshes are treated alike (spec 024 decisions 1, 2, 4, 5, FR-2; spec 002 FR-4; #78).
  4. Otherwise the run proceeds.
- **Running:** enters the download stage, reads the language setting and asks the source for its current version. A scheduled run whose version was already applied with the same sorted language set ends `skipped` with `<version> already applied` (rebuilding the name index first if it is empty), and still runs the source's `after_refresh` hook; a manual run applies again, and so does any run whose source's `#reapply?` says so (spec 002 FR-4; spec 011 AC-2.3, AC-3.1). `MTG::Scryfall::Source#reapply?` says so for two reasons: spec 011 AC-2.3's, printings with no artwork id, and spec 058 decision 3's, cards in the catalog and none with a mana value, so an upgraded instance fills the new column on its next refresh even when Scryfall's file is unchanged; the test is that none has one, not that any lacks one, as for artwork ids. Otherwise it downloads, syncs sets and entries, retires unseen entries and rebuilds the name index, in that order. It records each stage at once on entering it, and within a stage its done and total (when the source reports them) and its running counts as soon as `EVERY_RECORDS` records were seen or `EVERY_SECONDS` passed, and at most once per `AT_MOST_EVERY_SECONDS`; each write is also the heartbeat (`Catalog::Refresh::Progress`; spec 015 FR-1, AC-2.9, which allowed up to 5 seconds). A source that can't report how far through it is is still tracked by stage and counts (spec 015 FR-2, AC-2.8). A malformed record is counted as malformed and logged by its key, and a known entry whose record is malformed is kept, not retired; an entry whose set the source's set list lacks gets a set made from the entry's own set code and name (spec 002 FR-3).
- **Ends:** `applied` with its counts (seen, inserted, updated, retired, restored, malformed), then the source's `after_refresh` hook; `failed` with `"<error class>: <message>"`, the counts so far and the stage it reached, and the error re-raised for the job's retry rules; or `skipped` as above. Every finished run writes one structured log entry, `catalog.refresh.finished` (spec 002 FR-4, FR-5; spec 015 FR-1). A file with no valid records fails the run in the sync stage with `no valid records (<n> malformed)`, so it never reads as "everything was removed" (spec 015 Error Scenarios). A line of the file that isn't valid UTF-8 is one malformed line like any other the source can't read, and the run goes on; `MTG::Scryfall::Source` checks it before it strips or parses the line, because `String#strip` raises on it (#411). A failed run retires nothing, and the next refresh leaves the catalog as one successful run would (spec 002 FR-4, Reliability; spec 015 AC-3.8).

A start request while the refresh is in flight queues nothing and answers "A refresh is already queued or running." (spec 015 AC-2.3). The panel shows the most recent run not skipped as `already running` or `waiting for another job's retry` (`Catalog::RefreshRun.attempted`); the recent-runs list (`Catalog::Health::RECENT_RUNS`) shows every run, skipped ones included, with a failed one's plain sentence (spec 015 AC-2.16, AC-5.1; spec 024 FR-3, decision 4; #84). The recent-runs list and `catalog:status` call a run interrupted, or running with "no progress for N minutes", by the same rules as the panel (spec 015 AC-3.5, AC-3.9). The page has one panel per registered type (`Catalog::Health.all`), titled with the source's `.title` or the type's name, holding the refresh and then whatever the source's `.operations` hook adds, with no change to the admin code for a new type; a start request naming an unknown type or operation answers 404 and queues nothing (spec 015 AC-5.1–AC-5.3, AC-5.6). Each panel also shows the type's entry count (entries not retired), its last applied refresh and its next scheduled refresh, or "Not scheduled" (spec 015 AC-5.1, AC-5.5). `bin/rails "catalog:refresh[<type>]"` queues a manual refresh and returns; `bin/rails "catalog:status[<type>]"` prints the 10 most recent runs, skipped ones included, with the stored message, then any lines the source's optional `.status_lines` hook adds (spec 002 FR-5, AC-8.1; spec 011 AC-3.11).

### Art index build (`MTG::ArtBuild`)

Statuses: `running`, `finished`, `failed`, `skipped`. Only with art matching on (`COLLECTOR_MTG_ART_MATCHING`): with it off, or before the catalog's first applied refresh, a build job records nothing (spec 011 FR-1). `MTG::Art.after_refresh` queues one build job after a refresh that applied, or that was skipped as already applied while that version has no index at the current settings; a refresh skipped because another runs or waits queues none. An admin's "Build art index" queues one too (spec 011 AC-3.1; spec 015 AC-4.3, AC-4.9; spec 024 AC-1.3).

- **Start** (`MTG::ArtBuild.start!`, which reads the build jobs' queue and then, in one transaction, the builds): close as `failed`, message `interrupted`, each running build whose job id is the starting job's own, or that is left behind (`#left_behind?`: its heartbeat is older than `STALE_AFTER`, whether or not a worker holds its job, or older than `JOB_ENDED_GRACE` while its job is in the queue's failed list or, for a build started before the reading, held by no unfinished job; a build run with `MTG::Art::BuildJob.perform_now` in a console is outside the queue and judged the same way). Then skip the new build as `already running` if one still runs, or with `waiting for another job's retry` (`MTG::ArtBuild::WAITING_FOR_RETRY`) if another build job waits to run again; otherwise proceed (spec 011 AC-3.2; spec 015 AC-4.10; spec 024 FR-4; #73, #78). A skipped build shows nowhere: the panel and the status line read `MTG::ArtBuild.latest`, the latest build not skipped (spec 024 decision 4).
- **Running:** fails at once when ImageMagick is missing; otherwise fetches each artwork's image not yet cached and fingerprints the artworks without a fingerprint at the current settings, in batches of `BATCH`. It beats (heartbeat and counts) after every batch and, inside a batch, after an image once `BEAT_EVERY` has passed since the last beat (#73). It is incremental and resumable: cached images and stored fingerprints survive an interruption, and a complete build run twice changes nothing but its run record (spec 011 AC-3.5, AC-3.7, AC-3.8). An image that fails after its retries, or can't be decoded, is counted as failed and tried again next build; the build goes on (spec 011 AC-3.6).
- **Ends:** `finished` with its counts and the index file, written last (spec 011 AC-3.9); or `failed` with `"<error class>: <message>"`, and the error re-raised. A rate limit the client gave up on stops the build at once: its run fails, no image is counted as failed for it, and its job runs again, under the same job id, through `Catalog::RateLimitRetry`, its new build carrying on from the cache; the job is retried without limit while each rate limit comes with progress, and fails on the fourth in a row with no progress between them (spec 011 AC-3.6; spec 043; #74, #81). A busy database fails the run and the job retries, seconds apart, up to 3 attempts in all (`retry_on`); a missing ImageMagick (`MTG::Art::Decoder::Error`) fails it and the job is discarded (spec 011 Reliability; spec 015 Error Scenarios). A failed or interrupted build never removes the index in use (spec 011 Reliability).

The panel and the status line ask `MTG::ArtBuild#stalled?` (stale while a worker still holds the build's own job) before `#left_behind?`; `#left_behind?` is the one statement of the left-behind rule, asked by `MTG::Art::Operation`, `MTG::Art.status_line` and `MTG::ArtBuild.start!`, each reading the queue's build jobs first (#73, #79). A build job that starts closes a stalled build all the same (spec 015 Glossary "Stalled", AC-4.11).

### What the source does for a refresh (`MTG::Scryfall::Source`)

- The source version is the name of the current bulk file in Scryfall's bulk-data index: `default_cards` when only English is configured, `all_cards` otherwise (spec 002 FR-3).
- The download goes to `storage/catalog/<type>/` through a partial file of its own (`<file>.<random>.part`, a name per download, so two downloads of one version never share one: the price refresh is a second caller), renamed into place only when its size is the one Scryfall publishes (otherwise the partial is deleted and the run fails with `Catalog::Sources::IntegrityError`; a download that fails for any other reason deletes its own partial file too); a file of that size already there is used again, and only the `KEEP_DOWNLOADS` newest are kept; `prune` also deletes a `*.part` file whose mtime is older than `STALE_PARTIAL_AFTER`, so a killed download's orphan is cleared, and tolerates a file that vanishes under it (a concurrent download). The contract's comment says `#download` must tolerate concurrent calls for one version (spec 002 FR-3, Error Scenarios; spec 089 decision 1, which supersedes spec 002 FR-3's wording "a partial file"). It reports bytes received while downloading and compressed bytes read while the file is read, through `#progress=` (spec 015 FR-2).
- **One file for two refreshes.** An English-only instance's weekly refresh finds the day's file already on disk when the price refresh downloaded it first (the source reuses a file of the published size); an instance with languages beyond English reads `all_cards` (408 MB) and downloads it daily whichever job runs first, a cost the price refresh adds. The catalog refresh knows nothing of prices and records no analytics (design decision 10; spec 089 decision 1).
- The file is read record by record; printings in languages not configured, and digital-only ones, are left out before anything is written (spec 002 FR-3).
- Languages come from `COLLECTOR_MTG_LANGUAGES` (comma-separated codes); English is always included and is the default; a code Scryfall doesn't use fails the run before downloading, naming the code (spec 002 FR-6, Error Scenarios).
- Every request sends the app's `User-Agent` and an `Accept` header (`application/json`, or `image/jpeg` for an artwork image), waits `MIN_INTERVAL` after the previous one, and has explicit open and read timeouts; a refresh requests no single cards (spec 002 FR-3; spec 011 AC-3.4).
- A refresh asks the API host twice per run, `/bulk-data` before the download and `/sets` after it, at least `MIN_INTERVAL` apart; the bulk file comes from `data.scryfall.io`. Scryfall's documentation says the rate limits are those of `api.scryfall.com` and that "the direct file origins located at `*.scryfall.io` do not have rate limits" (https://scryfall.com/docs/api/rate-limits, read 2026-11-06), so the image origin is never rate limited, by its documentation; the client still treats a 429 from any of them as a rate limit (spec 043 Problem Statement, "Does the image host ever rate limit?").

### A rate-limited job

1. The Scryfall client (`MTG::Scryfall::Client`) waits what a 429's `Retry-After` asks for (seconds or an HTTP date), at most `MAX_BACK_OFF` seconds before a retry and never after its last of `MAX_ATTEMPTS`, so one call sleeps 60 seconds at most. A longer wait asked for, a 429 on the last attempt, or a 429 with no usable `Retry-After` on any attempt (a zero counts as none) raises `Catalog::Sources::RateLimitedError` at once, carrying the wait last asked for, or none (spec 002 FR-3; spec 011 AC-3.4; #74, #81). An image request also retries a 5xx, after its `Retry-After` or 1 and then 2 seconds; an API call raises at once on any other answer, and a download isn't retried (spec 011 AC-3.4; spec 002 Error Scenarios).
2. `Catalog::RateLimitRetry` reschedules the job after the wait the error carries, `SHORTEST_WAIT` at least, which also covers an answer that gave none. A wait over `LONGEST_WAIT` fails the job at once, progress or not. Otherwise the job is asked whether the attempt the rate limit ended made progress (`rate_limit_progress?`; a job that doesn't answer has made none). With progress the count of rate limits, kept in the job's retry record (`exception_executions`, under `COUNTED_AS`, as before), starts again at 1 and the job is retried; without it the count goes up by one and the job fails when that would pass `MAX_RETRIES`, that is on the fourth rate limit in a row with no progress between them. A failed job shows under Failed, and the next refresh or an admin starts another; an admin's retry starts the count again, as Solid Queue clears the record. The question is about the attempt the rate limit ended, alone (spec 043 decisions 1 and 2, FR-1 to FR-4; #86). The rule is tried before the job's own `retry_on` for transient errors, whose waits are a few seconds (spec 002 FR-4, Error Scenarios; #74, #81). `Catalog::RefreshJob` includes it (spec 002 FR-4), and so does `MTG::Art::BuildJob` (spec 011 AC-3.6).

   Progress is durable new work, as the operation judges it (spec 043 decision 3). For a refresh (`Catalog::Refresh#made_progress?`): a catalog row written, meaning a set, an identity or an entry inserted, updated or restored, or an entry retired; not the records seen, which the page shows, and not the download, fresh or reused. For an art build (`MTG::Art::Build#made_progress?`): an image fetched into the cache and kept, or a batch of fingerprints stored (up to `BATCH` at a time); not images found already cached, not the counts recorded at the start, not an image that failed or was removed as undecodable. With Scryfall a refresh is only ever rate limited on `/bulk-data` or `/sets`, before any row is written, so its count behaves as it did; the rule is still tested with a source that is turned away after writing (spec 043 decision 3).
3. While the retry waits, the job holds no concurrency lock and its run is already failed; a refresh or build of the same operation that starts meanwhile is skipped (`waiting for another job's retry`) and the waiting job does the work. The panel shows "Queued to retry" with "Retrying at" meanwhile (spec 024 Problem Statement, decision 1, AC-1.6, AC-2.3; #78). An admin can run the waiting job at once with **Retry now**: it moves the failed run's own job's scheduled entry to ready (`Catalog::Operation::Queue#run_now`), queues no job and changes neither the job's Active Job id nor its retry record, so the count carries on as for any retry; the move is atomic with one winner (the entry is removed first and the dispatch happens only when that removal happened), so a second press, a press as the wait ends or the queue's own dispatch changes nothing and the press says "Nothing is waiting to retry."; it is offered for any retry of that job, not only a rate limit's (spec 055 decisions 1–5, FR-2; maintainer ruling 2026-11-09; #77). The offer is decided in one place, `Catalog::Operation#retry_job_id` (the failed attempt's own job, held by the queue for a later time), which checks `unavailable_reason` first, so an operation that is switched off reads no record or queue for the page, and `Catalog::Operation#retryable?` is the one hook that narrows it; the page reads it for the button and for "Retrying at", and a press reads it again rather than trusting the page (spec 055 decision 1, FR-1, Error Scenarios).

### Not-loaded notice

While a catalog type isn't loaded, catalog search and the scanner say the card catalog hasn't been loaded yet, and so does the More page for an admin, naming each unloaded type when more than one is registered: an admin gets a link to `/admin/catalog`, a member is told to ask an admin, and a visitor (an open catalog) gets the first sentence only. Once loaded, no notice (spec 015 AC-1.1–AC-1.3, FR-6; spec 002 Error Scenarios "Catalog never loaded", changed by spec 015 FR-6; visitors changed by spec 023 decision 7).

### Jobs pages (`/admin/jobs`)

Filter chips Failed (the default), Running, Queued and Scheduled, each with its count. A list shows 25 jobs per page (`BackgroundJobs::List::PER_PAGE`) with class, short arguments (the arguments the job was queued with, not the queue's envelope), queue and the state's time, ordered by it: Failed by failed at and Running by started at, newest first; Queued by queued at and Scheduled by due at, oldest or soonest first. Queued jobs blocked by a concurrency limit are marked "waiting", and a failed row shows its exception class and the first line of its message; an empty state says there are none (spec 015 AC-6.1–AC-6.4). A job page shows class, full arguments, queue, priority, attempts since queued, its times and state, and for a failed job the exception, message and backtrace. Attempts since queued count the runs the job started, the one in progress included, across its own `retry_on` retries, starting again at an admin's retry (#61; spec 015 AC-6.5). A finished job still in the queue's records shows as finished with no actions, and a job whose class no longer exists renders with its recorded class name and can be discarded (spec 015 AC-6.5, Error Scenarios). Retry ("Retrying &lt;job class&gt;.") and "Discard…" (a confirm page, then "Discarded &lt;job class&gt;.") act on failed jobs only, through Solid Queue's own operations; a request for any other job changes nothing and answers "That job isn't failed any more.", or 404 when the job doesn't exist (spec 015 AC-6.6–AC-6.9). The pages are linked from the More page for admins (spec 015 AC-7.3) and from the header's account menu, which holds what the More page does on wide screens ([design system, More page](../design-system/components/MorePage.md)).

### Polling

`/admin/catalog` polls while any operation of any type is in flight; `/admin/jobs` and job pages poll while any job is running or queued, not for jobs that are only scheduled (spec 015 AC-2.10–AC-2.12, AC-6.10). The `poll` controller is rendered only then, and asks Turbo to refresh the page every `interval`; the layout's morph refresh keeps the scroll position, and the page's next render without the controller stops it (spec 015 FR-4; ADR 0015). Three pauses are rules, not accidents: a refresh is skipped while the tab is hidden, while Turbo is busy (`aria-busy` on `<html>`) and while a menu is open, because a morph would close it. The menu pause is page-wide: any open `<details>` holds it, and the admin pages' only `<details>` are menus. A tab shown again refreshes at once, if work is still in flight (the controller is still on the page), rather than at the next tick, and the other two pauses still hold at that moment; the `poll` controller listens for `visibilitychange` and removes the listener when it disconnects. The page is kept current by polling alone, never by broadcasts (rulings of 2026-11-09 on [#111](https://github.com/plainprogrammer/Collector/issues/111); ADR 0015).

## Decisions not in an ADR

- **Stalled is not interrupted.** A run or build with no progress past its threshold, whose job a worker still holds, reads as running or building, with the button disabled; restarting the app releases the job, which closes its own run and starts again (maintainer ruling 2026-10-09, spec 015 AC-3.6, Error Scenarios; #79 for the build).
- **The stall threshold is not the lock.** The 15-minute rule changes the start guard and the page; the 6-hour queue lock stays, so an interrupted refresh no longer blocks new ones for 6 hours (spec 015 FR-1, Open Questions).
- **A job is judged by its job only after the grace.** Within `JOB_ENDED_GRACE` a run whose job the queue failed may belong to a worker the queue lost sight of that still works, so it stays running (spec 015 Glossary, AC-3.9, AC-4.10; #60, #73).
- **Skip, not defer, while another job's retry waits**, for the refresh and the build, manual and scheduled alike; any waiting retry counts, not only a rate-limit one, however far off it is (a job held for later by hand makes every refresh of its type skip until it is due); the starting job's own retry never counts; a running run wins over a waiting retry; of two waiting retries the first due is skipped and the later does the work (spec 024 decisions 1–6, rulings 2026-10-14).
- **A refresh and an art build don't wait out each other's rate limit:** they ask different hosts, and the core can't tell whether two operations share a limit (spec 024 Non-Goals).
- **Two queued manual refreshes both apply**, one after the other; the second applies the same version again and changes nothing (maintainer ruling 2026-10-09, spec 015 Error Scenarios).
- **Loaded means an applied run**, per type; no download size is shown before the first refresh, since nothing calls the source during a render; no automatic first refresh (spec 015 Open Questions, AC-1.4).
- **Times** are absolute UTC in the form `9 Oct 2026 03:15 UTC`, with a relative form ("2 minutes ago") for last progress or heartbeat and for list times (spec 015 FR-8; `AdminHelper#utc_time`).
- **A graceful restart re-runs, a crash fails.** A graceful restart puts a running job back in the queue at once, and the job closes its own run and carries on; after a crash the queue fails the job once it notices the worker is gone (about 5 minutes), and the run reads interrupted by the job rule (spec 015 Error Scenarios; spec 011 Error Scenarios).
- **Progress is judged on the attempt the rate limit ended, alone.** In the order rate limit, a busy-database retry that did work, rate limit with no new work, the second rate limit counts 2, not 1: the job fails sooner than a perfect rule would, never later than before; the count stays in one place, the job's retry record (spec 043 decision 2).
- **A partial download file is per download (supersedes spec 002 FR-3's "a partial file").** A fixed `<file>.part` is shared by two downloads of one version, which the price refresh makes possible; a unique name makes a second download wasteful but harmless, and costs an orphan when a download is killed, which `prune` clears after `STALE_PARTIAL_AFTER` by mtime (a fixed-name partial file from an earlier build is caught by the same glob). The contract's comment carries the concurrent-call line (spec 089 decision 1; the implementation review found the vanishing-file race in `prune`).

**Accepted limits and open issues:**

- The art build's milliseconds-wide window between a failed build closing and its retry being queued is accepted: a second build in it goes ahead (spec 024 decision 4).
- A host suspended long enough for the queue to fail a working job can show its run as interrupted until the worker next records progress (normally within 2 seconds, up to about 70 in a hung request); a refresh started in that window closes it and runs beside it. A working build can do the same while one image takes more than 90 seconds (spec 015 Error Scenarios).
- When the database is too busy for a build to record its failure, or to open its run, the section reads "Building." or "Queued." with "Retrying at" instead of "Queued to retry" (spec 015 Error Scenarios).
- A skipped manual refresh behind a scheduled job's retry may end as "already applied"; and if the waiting retry later fails for good, the skipped work waits for the next weekly refresh or an admin (spec 024 decision 1).
- A refresh that fails after some batches committed leaves some cards with a mana value and some without; a scheduled run of the same version is then skipped as already applied (the reapply test needs none to have one), and the rest fill when Scryfall publishes a new file or on a manual refresh; spec 011's artwork test has the same gap (spec 058 Error Scenarios). If a source file ever carried no `cmc` on any card, `#reapply?` would stay true and each scheduled run would parse the file again, writing nothing because the digests match; it is asked once per run, so it is no loop (spec 058 implementation review).
- A finished build is judged by its file's name only: a damaged file still reads "Ready." (spec 039 Non-Goals, maintainer ruling 2026-11-03). Settings and catalog drift are judged from the build's row, not the file's header, and for the latest finished build, not for the newest file the scanner serves; the two are the same file unless files were removed by hand or a later build failed (spec 053 Non-Goals; #176).
- A release that changes `config/art_fingerprint.json` queues no rebuild by itself: only a catalog refresh does (`MTG::Art.after_refresh`), so until the next refresh or a press of **Build art index** the scanner reads text only and the admin page says "Out of date" (spec 053 Non-Goals; maintainer ruling 2026-11-09, noted as open).
- An admin can run a waiting retry now (spec 055; [#77](https://github.com/plainprogrammer/Collector/issues/77)) but can't discard one from `/admin/jobs`, which discards only failed jobs (maintainer ruling 2026-11-09 on #77: out of scope).
- [#41](https://github.com/plainprogrammer/Collector/issues/41): backup and restore of an instance isn't built; whether a backup holds the catalog downloads and the art index under `storage/catalog/`, which can be rebuilt, is left to its ADR.
