# Data portability

How a collector's collection leaves and enters Collector: the export format, the export download, the import preview and the apply, and how they relate to an instance backup. This is the current truth; the specs it distils record what each feature promised when it shipped (see Sources and the [specs index](../specs/README.md)). The format itself is defined by [`docs/export-format/README.md`](../export-format/README.md) with `v1.schema.json` to `v4.schema.json` and `examples/` beside it; this doc points to it and does not restate the schema.

## Scope

**Covers:**

- The export format's rules for the app: which versions the app reads and writes, how it keeps its schema copies, the rules a schema can't state, and the coverage guard (`ExportFormat::Rules`, `app/models/export_format/v<N>.schema.json`, `spec/export_format_document_spec.rb`, `spec/export_format_examples_spec.rb`; spec 017; ADRs 0020, 0021, 0023, 0025).
- The export: `CollectionExport`, `GET /collection/export`, `Collections::ExportsController` (spec 022; spec 029 AC-6.1–AC-6.8; spec 032 Story 8; spec 062 Story 6).
- The import preview: `CollectionImport`, `CollectionImport::Locations`, `CollectionImport::Decks`, `CollectionImport::Proxies`, `CollectionImport::ProxyRows`, `Collections::ImportPreviewsController`, the views under `app/views/collections/import_previews/` (spec 025; spec 029 Story 8; spec 032 Story 10; spec 062 Story 7).
- The apply: `CollectionImport::Plan`, `CollectionImport::Apply`, `CollectionImport::LocationChanges`, `CollectionImport::DeckChanges`, `CollectionImport::WorkingState`, `Collections::ImportsController` (spec 028; spec 029 Story 9; spec 032 Story 11; spec 062 Story 8; ADR 0022 as far as the apply reads the stored upload).
- Version 4: decks, proxies and a lot in a deck's zone in a file, and how a file's decks, zones and proxies are read, previewed and applied (spec 062 decision 4, Stories 6–8, FR-3; ADR 0028; spec 068 decisions 14–18, Story 7).
- That the number-entry list and the scanner sitting are left out of the export (spec 026 decision 6, FR-5), and the guidance on when to use an export and when a backup (spec 030 decision 11).

**Neighbours:**

- The lot as the unit of ownership (ADR 0019), `Lot`, and locations as a feature (`Location`, `Location::Name`, `/locations`, spec 029 apart from its export and import parts) and a lot's place in the collection (`Lot#location`, Move copies, `Location::Holdings`, spec 032 apart from the export, preview and apply) are **[collection and lots](collection-and-lots.md)**, and so are decks and zones as locations (`Deck`, `Deck::Creation`, the Decks pages, the format seam `Catalog::Formats`, the label "Deck › Zone" and `Location::Placement`'s label, spec 062 apart from Stories 6–8). This doc uses that a deck is a location of kind `deck` with a `decks` row (collectible type and format), that a zone is a child location a lot may sit in, and that the registrations say a format's zones.
- The stored upload's retention: `ImportUpload`'s expiry, the sweep, the orphan rule, the Active Storage routes' gate and the 40 MB request body caps in Puma, Thruster and kamal-proxy are **release and deploy** (spec 028 decision 9; spec 025 decision 6; ADR 0022). This doc uses only that an upload is stored for an hour, one per account, and is gone when it is applied or refused.
- Backup and restore of an instance (`backup:create`, `backup:restore`, `docs/backup-restore.md`) is **release and deploy** (spec 030).
- Catalog lookups the preview makes (`Catalog.collecting`, `Catalog::Entry`) are **[catalog core](catalog-core.md)**.

## Glossary

- **File / export:** one JSON document in the `collector-export` format that describes one account's collection at one moment (spec 017 FR-1).
- **Well-formed / resolvable:** well-formed depends on the file alone; resolvable on the file against one instance's catalog (spec 017 Glossary; format document).
- **Entry identity / lot identity:** collectible type and source id; and entry identity, finish, condition, price paid and, from version 3, the lot's location by comparison key: six values, the sixth `null` for versions 1 and 2 and for a lot in none, and from version 4 also a pair, a deck's comparison key and a zone key, for a lot in a zone (spec 017 Glossary; ADR 0019; spec 032 FR-3, ADR 0025; spec 062 decision 4, AC-6.12; ADR 0028).
- **The same collection:** the format's equality of two files: profile, currency, lots as sets (with quantity and both times), from version 2 locations as sets of names compared as written, from version 3 each lot's `location` compared as written too, and from version 4 decks as sets of `name`, `collectible_type` and `format` as written, a zone's `location` by its deck's name as written and its key, and proxies as sets of deck name as written, zone key, entry identity, finish and quantity (spec 068 AC-7.3; spec 017 FR-7; spec 029 decision 9; spec 032 AC-9.6; spec 062 AC-6.13).
- **Row:** one element of the file's `lots`, numbered from 1; row N is `/lots/N-1` (spec 025 Terms).
- **Problem row:** a row that can't be applied, for any reason in the row-problem table below (spec 025 Terms).
- **Held lot:** a lot in the collector's collection (spec 025 Terms).
- **Outcome:** added, changed, unchanged, held by a problem row or removed, for lots; added, renamed, unchanged or removed, for locations; the same and *format changed* for decks, which a deck can be together with renamed (spec 025 decision 1; spec 029 decision 10; spec 062 AC-7.2).
- **Plan:** what applying the file to the collection as it is now would do (spec 028 Terms; `CollectionImport::Plan`).
- **Fingerprint:** a SHA-256 digest of the stored file's checksum and the plan; stored with the upload and carried in the apply form (spec 028 Terms, decision 2).
- **Nothing to change:** a plan with no added, changed or removed lot, no added, renamed or removed location, no added, renamed, format-changed or removed deck, no view change and no currency change; the zone repair of an apply (below) is never a change of its own (spec 028 Terms, decision 12; spec 029 decision 10; spec 038 decision 7, AC-6.5; spec 062 AC-7.7, AC-8.2a).
- **Comparison key:** the Unicode full case folding of a location's name after normalisation; a place's or a deck's identity in a file and in an account, the two sharing one name space (spec 029 decision 5, ADR 0023; spec 062 decision 4).
- **Deck / zone key / format:** a file's deck is `{ name, collectible_type, format }` (the format's key, unique within its type); a zone is never listed, it is named by a lot's `location` as `{ deck, zone }`, the deck by its comparison key and the zone by its key, and a deck's zones come from its format's registration on the instance reading the file (spec 062 decision 4; ADR 0028).
- **Proxy:** a file's proxy is `{ deck, zone, entry, finish, quantity }`: the deck by its name, the zone by its key, the entry as a lot's, a finish (a string or `null`) and a quantity of 1 to 9,999; its identity is the deck's comparison key, the zone key, the entry's type and source id and the finish; it carries no time. A proxy is never a lot (spec 068 decisions 1, 14). In the import, a count of proxies is rows, as a count of lots is lots (spec 068 Terms, decision 16).
- **Registration:** what a collectible extension gives the core for its formats and their zones (`Catalog::Formats`); `unknown_format` and `unknown_zone` depend on it, so they are the reader's resolvable checks, with `unknown_type` (spec 062 AC-6.11; ADR 0028).
- **Stored upload:** the previewed file kept briefly so that it can be applied (spec 028 decision 1).

## Invariants

- **The format document is the format's definition.** The app's schema copies are byte-identical to the ones in `docs/export-format/` (one per version), and the suite fails if they differ (ADR 0021; spec 029 AC-7.6).
- **No internal id appears in a file.** A lot points at its entry by collectible type and source id, a place and a deck are their names, a zone is its deck's name and its key, a proxy is its deck's name, its zone's key and its entry, and a file carries no account or user id (spec 017 FR-1, FR-6, AC-1.4; spec 029 AC-6.5; spec 062 AC-6.5).
- **The meaning of a released version never changes.** A version rises when an older reader would misread a file or lose collector-owned data; a new field of collector-owned data raises it, an information-only field doesn't (spec 017 FR-8, decision 14; ADR 0020; ADR 0023). Version 2 added locations; version 3 added each lot's `location` (spec 032, ADR 0025); version 4 adds `decks`, a lot's zone and `proxies` (spec 062, ADR 0028; spec 068: a file's `proxies` is required, and version 4 was unreleased when it was added).
- **A new table with `account_id` or `user_id`, or a new column on `accounts`, `lots`, `users` or `locations`, fails the suite** until the format document's Coverage tables list it; `decks` and `locations.kind`, `parent_id` and `zone` were listed with version 4, and `deck_proxies` with its proxies (spec 017 FR-9, AC-3.4, AC-3.5; ADR 0020; spec 062 AC-9.10; spec 068 AC-7.3).
- **The core names no collectible.** The export's, the preview's and the apply's code contain neither `MTG` nor `Scryfall`; the export never asks the catalog registry about a type, so a lot of a type the instance no longer has still exports (spec 022 FR-6, decision 4; spec 025 FR-9; spec 028 FR-8; spec 029 FR-2). Checked by `spec/collection_export_core_spec.rb`, `spec/collection_import_core_spec.rb`, `spec/import_apply_core_spec.rb`; the last also lists the location files, and `spec/deck_core_spec.rb` the import's deck files (`Decks`, `DeckChanges`, the preview's deck partial), which also name no format and no zone key but `considering` (spec 062 FR-3, AC-9.11).
- **Everything runs through `Current.account`.** No parameter names an account, an upload or a lot; the one parameter besides the confirmation is the fingerprint (spec 022 Security; spec 025 FR-5; spec 028 FR-5, AC-4.2). Another account's data never appears in a response (spec 022 AC-2.1; spec 025 AC-4.1; spec 028 AC-4.1).
- **An export is built in the request and stores nothing.** No job, no row, no file, no cache entry (spec 022 decision 1, FR-3).
- **The preview never writes a lot, user, location or account and never enqueues a job.** The one thing it may write is the account's stored upload, and only for a file that can be applied and has something to change (spec 025 FR-6 as superseded by spec 028 decision 10, AC-1.11; spec 029 AC-8.8).
- **A file's content is never logged or echoed.** A JSON parse error's message is dropped, the `export_file` field is in `filter_parameters`, and the apply logs an error's class and backtrace but not its message (spec 025 FR-6; spec 028 FR-6).
- **Responses of the export, the preview and the apply carry `Cache-Control: no-store`** (spec 022 AC-1.1; spec 025 Security; spec 028 FR-6).
- **Applying is all or nothing,** in one write transaction; it replaces the collection, the locations and, from version 4, the decks and the proxies with the file's, never merges, and applies a file only when it has no problem row (spec 025 decisions 1, 2; spec 028 decisions 3–5; spec 029 decision 11).
- **What is applied is what was previewed.** The form's, the stored and the recomputed fingerprints must be equal, or nothing is written (spec 028 decision 2).
- **Applying the same file twice leaves the collection as the first left it:** the second is refused as nothing to change and writes and clears nothing (spec 028 decision 12, AC-2.2; spec 029 AC-9.7).
- **Applying never changes the collector's name or email address,** only `collection_view` and only to a view the instance knows (spec 025 decision 4; spec 028 decision 5).
- **A changed lot, a renamed location and a renamed or format-changed deck keep their ids** (a deck's zones and lots stay with it), and an unchanged one isn't written, not even its `updated_at` (spec 028 FR-9, decision 5; spec 029 decision 10; spec 062 AC-8.2).
- **Removing a location never changes a lot** (spec 029 decision 3, AC-9.11) and a location that holds a lot can't be removed, so an apply deletes the lots of a location it removes, and of a removed deck's zones or a zone a format change drops, before the location (spec 032 decision 3, AC-11.6; ADR 0025; spec 062 AC-8.6). It never moves a lot to make a removal succeed.
- **An older file's lots are unplaced.** A version 1 or 2 file says nothing about a place, so its lots are read as in none, match only unplaced held lots, and the preview says so (spec 032 decision 7, AC-10.4; ADR 0025).
- **A version 1 to 3 file leaves the decks and removes the copies in them.** It has no way to name a zone, so a held lot in a zone is a removed lot ("in Izzet Tempo › Main"), the deck and its zones stay, and applying it needs the removal confirmation (spec 062 AC-7.4, AC-7.6; ADR 0028). A version 4 file replaces the decks like the places, and an import places lots in zones as the file says: it moves nothing into Considering when it changes a deck's format, because a file is the truth; the move into Considering is the app's change of format, which spec 064 added ([collection and lots](collection-and-lots.md), "A deck"), and an import still moves none (spec 062 AC-8.2; spec 064 Non-Goals). A deck whose format was changed in the app exports its new `format` and its lots' new zone keys, and applying that file on the same instance is "nothing to change"; the format document is unchanged (spec 064 decision 7, AC-1.8).
- **A file of version 4 names every proxy; an older file leaves them alone.** `proxies` is a required list of version 4 (an `edge` image's version 4 file without it is not supported: it is refused as any schema-invalid file is, naming `proxies`, never a row problem; no release wrote one). A version 4 file replaces the collector's proxies with its own, as it replaces the decks and the lots, and removing any needs the confirmation. A version 1 to 3 file can name none, as it can name no deck, so it leaves every proxy as it is (it removes no deck either), the preview says "This file was written before proxies existed, so your proxies would stay.", and its fingerprint holds nothing of them. An import never moves a proxy into Considering (spec 068 decisions 14–16, AC-7.5, AC-7.8).
- **A place and a deck share one name space and one limit of 500 in a file as in an account.** A comparison key is a place or a deck, never both, so a file that gives a held place's key to a deck removes the place and adds the deck (spec 062 decision 3, AC-6.8, AC-6.9, AC-7.3).
- **Working state is left out of the export and cleared by an apply that writes a lot:** the number-entry list, the scanner sitting (with the place and the condition chosen for it, which add no coverage entry or format version), bulk selections and bulk removals' undo (spec 026 decision 6, FR-5; spec 028 decision 7; spec 029 decision 11, AC-9.17; spec 040 decision 5, AC-5.3; spec 042 decision 6, AC-5.3). An apply that removes only a location clears a sitting's place through the foreign key and keeps the sitting (spec 040 AC-3.2).
- **Only a signed-in collector reaches any of these pages;** a signed-out request is sent to sign in and the reader isn't called (spec 025 AC-4.2; spec 028 AC-4.3). Signing in from the export lands on the collection, not on the file (spec 022 decision 9).

## States and transitions

### The export (`CollectionExport`)

`GET /collection/export` (route `resource :export, only: :show, format: false`) sends the file as an attachment named `collector-export-<UTC date>.json`, type `application/json` (spec 022 decisions 2, 3, AC-1.1). It always writes the newest version, 4, with `locations`, `decks` and `proxies` present and empty for an account with none and every lot's `location` present (`null` for a lot in none, never an empty string; a place's name; or `{ "deck": <the deck's name as stored>, "zone": <the zone's key> }` for a lot in a zone); it doesn't fall back to an older version (spec 029 decision 2, AC-6.1, AC-6.2; spec 032 AC-8.1, AC-8.6; spec 062 AC-6.1, AC-6.3). Contents:

- `profile` and `currency` (the account's own, `accounts.currency`; `generator` is left out because the app doesn't know its version) (spec 022 decisions 4, 5; spec 038 decision 6, AC-5.1).
- `locations`: the places only, names only, ordered by comparison key then name in code-point order, read in one query; never a deck or a zone (spec 029 decision 2, FR-3; spec 062 AC-6.2).
- `decks`: each deck's `name` as stored, `collectible_type` and `format`, ordered by comparison key then name in code-point order, read in one query; zones are not listed, they come from the format (spec 062 AC-6.1; ADR 0028).
- `proxies`: each proxy's deck name as stored, its zone's key, its entry as a lot's, its `finish` and `quantity`, read in one statement joining `deck_proxies` with the entry and its set and the zone, its deck and the deck's row, ordered by the deck's comparison key and name, the zone key, the entry's type and source id and the finish; never a time or an id, never a lot (spec 068 AC-7.1, AC-7.2).
- `lots`: read in one statement joining `lots`, `catalog_entries`, `catalog_sets` and, by left joins (`Lot.with_place`), the lot's place, its parent and the parent's `decks` row, so each lot's `location` and a zone's deck name, key, type and format come from the same statement, ordered by lot id; the writer formats times (UTC, fraction dropped, not rounded) and prices (exact, two places) itself (spec 022 decisions 4, 8, AC-1.4).

The lots, the proxies, the places and the decks are four reads, and a rename or removal of a place or deck between them would leave a lot or a proxy naming one the lists lack (and a change of a deck's format a zone its listed format may lack), so the reads are repeated up to `TRIES` (3) times and then `CollectionExport::Unsettled` is raised (spec 032 AC-8.3, plan review M5; spec 062 AC-6.4). The number of queries doesn't depend on the number of lots, places or decks (spec 022 AC-1.8, FR-2; spec 032 NFR). Two exports of an unchanged collection are identical apart from `exported_at` (spec 022 AC-1.6; spec 029 AC-6.6). Nothing of a scanner sitting, a number-entry list or any other working state is in it (spec 022 AC-2.2, decision 7; spec 026 decision 6).

### Reading a file (`CollectionImport`, `ExportFormat::Rules`)

The checks run in this order and the first that applies refuses the whole file (preview: 422, the upload page with the reason and no rows) (spec 025 decision 10, AC-3.1; spec 029 decision 10):

| # | The file | Rule | Reason shown (summary) |
|---|---|---|---|
| 1 | No file, empty, or not an upload | `no_file` | "Choose an export file to preview." |
| 2 | Over `MAX_BYTES`, refused before parsing | `too_large` | larger than 32 MB |
| 3 | Not UTF-8, not JSON, a byte order mark, or an object with a key twice | `not_utf8`, `not_json` | "isn't readable JSON" |
| 4 | Not an object; `format` missing or not `collector-export` | `type`, `required`, `const` | "isn't a Collector export" |
| 5 | `format_version` missing, or not a whole number of at least 1 | `required`, `const` | "doesn't say which version" |
| 6 | `format_version` higher than 4 (`5` or `5.0`) | `newer_version` | "written by a newer version … This instance reads version 4." |
| 7 | A schema problem outside `/lots/<row>` and, from version 4, `/proxies/<row>` (header, profile, currency form, `lots`, from version 2 `locations`, from version 4 `decks` and `proxies` (a missing or non-list `proxies` refuses the file), including `duplicate_location`, `maxItems` and, from version 4, `too_many_locations` at `/decks`), or `exported_at` not a real moment; a name of `locations` (version 2 on) or of a deck (version 4) whose NFC form is over 60 code points | the keyword, `duplicate_location`, `too_many_locations`, `not_a_time`, `maxLength` | "isn't a well-formed export: `<field>` …", naming the first such field in document order |
| 8 | `currency` well-formed but not one of the 20 codes `Collector::Currency::SYMBOLS` knows | `unsupported_currency` | "Collector can't show prices in XYZ." (spec 038 decision 7, AC-6.6) |
| 9 | Version 4: a deck whose `collectible_type` and `format` this instance doesn't register (the first, at `/decks/<i>/format`) | `unknown_format` | "This instance doesn't know the format “<format>” of <type>." (spec 062 AC-6.11) |
| 10 | Version 2 or 3: a place of the file with the comparison key of a held deck (the first, at `/locations/<i>`) | `deck_name_taken` | "A deck you have is called “<name>”, like a place in this file. Rename one of them and preview again." (spec 062 AC-7.4a) |
| 11 | Version 2 or 3: the file's places and the held decks together over 500 | `too_many_with_decks` | "This file and your decks together would have more than 500 locations." (spec 062 AC-7.4b) |

The version is read before the schema, so a newer file is refused as newer, not as malformed; a file with a missing or unknown version is judged by version 1's schema, which names the version (spec 025 decision 10, AC-3.2; format document, Well-formed). A version `1.0` or `2.0` is read as 1 or 2 (spec 025 AC-3.2). The content is judged, never the declared type or name (spec 025 decision 6, AC-3.5). The app checks the lots one at a time against the schema's `$defs/lot`, and the rest of the file with its lots left empty, to bound memory; a schema that moves the lot elsewhere changes this (ADR 0021 amendment). A version 2 or 3 `locations` over 500 is reported at once and only its first 500 are checked (spec 029 review M1); from version 4 the `locations` and the `decks` together over 500 are reported at once as `too_many_locations` at `/decks`, and only the first 500 of each list are checked, so what a hostile file costs doesn't grow with the lists (spec 062 AC-6.9; `ExportFormat::Rules.names_over_limit?`). Rows 9 to 11 are the reader's, not the format's: `unknown_format` depends on this instance's registrations, like `unknown_type` and `unsupported_currency`, and the two older-file refusals on the collector's own decks, so the format document lists `unknown_format` and `unknown_zone` under "resolvable" and none of the three is among `ExportFormat::Rules::RULES` (spec 062 AC-6.11, AC-7.4e). They come after `unsupported_currency` and before any row is judged, in that order, and the first that applies decides the reason (AC-7.4e); a version 1 file has no places, so neither older-file refusal applies to it. The deck whose name is long only once normalised is the format's own rule (`maxLength` at `/decks/<i>/name`, `ExportFormat::Rules.long_deck_names`), where a place's long name is the reader's check (`long_location`), so that every invalid example of the document fails for exactly one reason (spec 062 AC-6.7b).

**Row problems** (a well-formed file whose row can't be applied). A row that isn't well-formed is not checked against the catalog; a well-formed row is checked in this order: type, then entry (and condition), then finish and condition (spec 025 decision 9, AC-2.4, AC-2.5; spec 028 1.3.4):

| Problem | Rule | Reason shown |
|---|---|---|
| Row not an object; required field missing; wrong type, form or range | `type`, `required`, schema keywords | "This row isn't a lot"; "`<field>` is missing"; "`<field>` isn't valid" |
| A time that isn't a real moment | `not_a_time` | "`<field>` isn't a real moment" |
| `changed_at` before `added_at` | `changed_before_added` | "changed_at is earlier than added_at" |
| Same identity as an earlier row | `duplicate_lot` | "Same card, finish, condition and price as row M" for versions 1 and 2; "…, price and location as row M" for versions 3 and 4 (spec 032 AC-9.5; spec 062 AC-6.12) |
| From version 3, a lot's location the file's `locations` don't list (by comparison key); from version 4, a `{ deck, zone }` whose deck the file's `decks` don't list | `unknown_location` | "Its location “Box” isn't one of the file's locations." (spec 032 AC-10.3); "Its deck “Izzet Tempo” isn't one of the file's decks." (spec 062 AC-6.10, AC-6.7a) |
| Collectible type the instance doesn't have | `unknown_type` | "This instance doesn't collect `<type>`" |
| Entry not in the catalog (retired entries are in it) | `not_in_catalog` | "Not in this instance's catalog" |
| Finish the entry doesn't list | `finish_not_listed` | "This printing doesn't come in `<finish>`" |
| Condition not one of the type's | `condition_unknown` | "`<condition>` isn't a condition this instance knows" |
| From version 4, a lot in a zone key the listed deck's format lacks (checked only for a row with none of the problems above) | `unknown_zone` | "The deck “Izzet Tempo” has no zone “side” in its format." (spec 062 AC-6.10, AC-6.7a) |
| Price over `MAX_PRICE_CENTS` in cents | `price_too_large` | "price_paid is too large to record" |

A row's identity can be read when its entry type and source id are non-blank strings and its finish, condition, price and (version 3 and later) location pass the schema; a row that fails `unknown_location` keeps a readable identity, so the held lot it matches is held, not removed (spec 032 AC-10.3; spec 062 AC-6.10); a row whose identity can't be read matches no lot (spec 025 decision 1). Descriptive fields never matter: when they disagree with the catalog the id wins and the row is fine; a retired entry is fine (spec 025 AC-2.2, AC-2.3; format document). Entries are looked up by (`collectible_type`, `external_key`), retired or not, in a number of statements that doesn't grow with the rows (spec 025 FR-3, FR-4).

**Proxy rows** (version 4; spec 068 decision 18). The file's proxies are checked one at a time against the schema's `$defs/proxy`, and a problem under `/proxies/<row>` is a problem row of that proxy, listed apart from the lot rows as "Proxy N", never a refusal of the file. The rules, in order: the schema's keywords (type, required fields, no other field, `quantity` 1 to 9,999, `entry`'s form); `duplicate_proxy` ("Same deck, zone, card and finish as proxy M"); `unknown_location` for a deck the file's `decks` don't list ("Its deck “X” isn't one of the file's decks.", at the proxy's `deck`); then the reader's, for a row with none of those: `unknown_type`, `not_in_catalog`, `finish_not_listed` (a non-null finish the entry doesn't list) and `unknown_zone` (the deck's format lacks the key). A proxy with no finish is never a problem, and the reader never compares a proxy's collectible type with its deck's, because a change of format can switch a deck's type (spec 068 decisions 2, 19). `duplicate_proxy` and the extended `unknown_location` are rules of the format (`ExportFormat::Rules::RULES`); the rest depend on this instance's catalog and registrations. A file with a problem proxy row can't be applied.

### Outcomes of a plan

For lots, comparing rows with held lots by identity (six values; a held lot in a place has the place's comparison key as the sixth, a held lot in a zone the pair of its deck's comparison key and its zone key (`Location::Placement`), so the same printing in two decks' "Main" is two held lots, and a place called "Box" and the zone `main` of a deck called "Box" are different places (spec 062 AC-6.12, AC-7.4c); so a version 1 or 2 file's rows, whose sixth is `null`, match unplaced held lots only: a placed lot is removed and its row added, or changed against an unplaced twin) (spec 032 AC-10.2, AC-10.4, AC-10.5); each held lot has exactly one outcome, taken in this order (spec 025 decision 1, AC-1.2, AC-1.6, AC-1.11):

| Outcome | When |
|---|---|
| Added | a row that isn't a problem row whose identity no held lot has |
| Changed | such a row whose identity a held lot has, with another quantity, `added_at` or `changed_at` (compared to the second; `4.0` is `4`) |
| Unchanged | the same, with equal quantity and times |
| Held by a problem row | a held lot no good row matches, whose identity a problem row has; it is never removed |
| Removed | any other held lot |

For locations in a version 2 or 3 file, held locations become the file's, matched by comparison key after each file name is normalised on read (spec 029 decision 10, AC-8.2, AC-9.18):

| Outcome | When | Applying does |
|---|---|---|
| Added | the file has a key no held location has | creates it |
| Renamed | a held location has the key but not exactly the name ("box" and "Box") | respells it; its id stays |
| Unchanged | a held location has exactly the name | writes nothing |
| Removed | a held location whose key no file location has | deletes it; no lot changes |

For decks in a version 4 file, the same way, matched by comparison key in the one name space (`CollectionImport::Decks`; spec 062 AC-7.2):

| Outcome | When | Applying does |
|---|---|---|
| Added | the file has a key no held deck has | creates the deck, its location and one zone per zone of its format |
| Renamed | a held deck has the key but not exactly the name | respells the deck's location; its id, zones and lots stay |
| Format changed | a held deck has the key but another `collectible_type` or `format` | keeps its id and name, takes the new type and format, gets the zones of the new format it lacks and loses those the new format lacks (the lots of those zones are among the removed lots; none is moved into Considering) |
| Unchanged | a held deck has the key, the name, the type and the format | writes nothing |
| Removed | a held deck whose key no file deck has | deletes its zones and the deck; the lots in its zones are among the removed lots (the file's rows can't name them) |

Renamed and format changed are independent: a deck with both is in both lists and counts, and in both parts of the fingerprint. A key is a place or a deck: a held place the file spells as a deck is removed and the deck added, and the other way round, and the preview says so in both sections (spec 062 AC-7.2, AC-7.3).

For proxies in a version 4 file (`CollectionImport::Proxies`), compared by identity (the deck's comparison key, the zone key, the entry and the finish; spec 068 decision 16):

| Outcome | When | Applying does |
|---|---|---|
| Added | a good row no held proxy has | inserts it |
| Changed | a good row whose held proxy has another quantity | sets the quantity; the id and `created_at` stay |
| Unchanged | a good row equal to a held proxy | writes nothing |
| Removed | a held proxy no good row matches, including the proxies of a deck or zone the file drops and any a problem row alone names (the preview can't be applied then) | deletes it, before the zones and decks it sits in |

A version 1 file says nothing about locations: they stay, the preview says "This file was written before locations existed, so your locations would stay as they are.", and its fingerprint holds nothing of them (spec 029 decision 10, AC-8.4, AC-9.3). A version 1 or 2 file also says "This file was written before lots could be in a location, so its lots would be in none." (spec 032 AC-10.4). A version 1 to 3 file says nothing about decks: no deck counts, the decks stay, and the preview says "This file was written before decks existed, so your decks would stay, but the copies in them (<N> lots) would be removed." (the second part only when a deck holds a lot; those lots are the removed lots "in Izzet Tempo › Main") (spec 062 AC-7.4), and the same paragraph adds "This file was written before proxies existed, so your proxies would stay." (spec 068 AC-7.8).

The profile: `collection_view` changes only to the other of `User::COLLECTION_VIEWS` (`grid`, `table`); a view the instance doesn't know is ignored, no line, no problem; a differing name or email address is shown as information and never applied (spec 025 decision 4, AC-1.7).

The currency: a file in any of the 20 codes is read, and applying it sets the account's currency to the file's (`Plan#currency_change`, from the account's to the file's, nil when they are equal). The Profile section then starts "Your prices would be shown in EUR instead of USD. Nothing is converted."; a removed lot's price is written in the account's current currency and a problem row's in the file's (spec 038 decisions 7, 8, AC-6.1–AC-6.8).

### The preview page

`GET /collection/import_preview/new` is the upload page; `POST /collection/import_preview` renders the preview (200) or the upload page with the reason (422); both forms are submitted without Turbo Drive (spec 025 decision 8, AC-1.1). The preview shows, in order: the file (export time, row count, currency); whether it can be applied; the "catalog not loaded" notice for the types the file names; the counts of the lot outcomes; the apply form (below); the profile notes; removed lots, each ending "in <location>" when it was in one; the Locations section (version 2 and later) or the version 1 sentence; the Decks section (version 4) or the older file's sentence above; problem rows, a row ending "in <location>" with the file's spelling; problem rows with counts by reason (spec 025 decision 9; spec 028 AC-7.1; spec 029 decision 10). The Decks section has the counts "Decks added", "Decks renamed", "Format changed", "Decks unchanged" and "Decks removed", and lists the renamed (old → new), the format-changed ("Elves: First format → Second format", each side prefixed by its collectible's heading only when the two belong to different collectibles) and the removed decks (spec 062 AC-7.1). The Proxies section (version 4) has the counts "Proxies added", "Proxies changed", "Proxies unchanged" and "Proxies removed" (rows) and lists the first `LIST_LIMIT` removed proxies, each with its card, its set line and "in <Deck › Zone>", then "and N more"; the proxy problem rows have their own section, "Proxies with problems", with counts by reason (spec 068 AC-7.6, AC-7.7). A removed lot or a problem row naming a zone ends "in <Deck › Zone>", the file's spelling for a problem row, with the zone's name as the deck's format registers it and its key when the format has none (spec 062 AC-7.5). Each list (problem rows, removed lots, renamed locations, removed locations, and the three deck lists) shows its first `LIST_LIMIT` entries then "and N more"; the counts cover all (spec 025 decision 11, AC-2.8; spec 029 AC-8.9). A file with problem rows says it can't be applied and offers no apply (spec 025 decision 2; spec 028 decision 4).

### The stored upload and the apply form

A preview stores the file only when it can be applied and has something to change; a refused file, a file with problem rows and a file with nothing to change store nothing and leave an earlier stored upload alone (spec 028 decision 1, AC-1.11, AC-5.2). A new storing preview replaces the account's one stored upload, with the plan's fingerprint (spec 028 decision 1; ADR 0022). The apply form carries no file field, only the fingerprint and, when the plan removes a lot or a location, a required checkbox "I understand this removes N lots, M locations, K decks and P proxies" (the parts that apply; the lots in a deck's zones count among the lots, so applying an older file over decks that hold copies needs it), after a link to download the current collection (spec 028 decisions 6, 11, AC-1.1; spec 029 AC-9.10). If storing fails, the preview shows its counts, no apply, and says the file couldn't be kept (spec 028 Error Scenarios).

### The apply (`POST /collection/import`)

Everything that can be done before the lock (reading the stored file, parsing, judging, resolving, building the rows) is done first; then one write transaction re-checks and writes (spec 028 decision 3, FR-2). Checks run in this order and the first that applies decides the response (spec 028 decision 13, AC-3.6):

| # | Situation | Response |
|---|---|---|
| 1 | No stored upload, or it is past its expiry, or its file can't be read | 422, upload page: "Preview the file again." / "Your preview has expired. Choose the file again."; an expired or unreadable upload is removed (AC-3.3, AC-2.5, AC-5.6) |
| 2 | The stored file is now refused or has problem rows (the catalog changed); for a version 1 to 3 file also when the collector's decks now meet its places (`deck_name_taken`, `too_many_with_decks`), judged again by `replan` inside the write transaction on what it holds then, before the nothing-to-change and fingerprint checks, so such a refusal is never shown as a stale preview offered again | 422 with the preview's reasons; the upload is removed (AC-3.4, decision 4; spec 062 AC-7.4d) |
| 3 | The plan has nothing to change | 422 "This file has nothing to change"; nothing written or cleared; the upload is removed (decision 12, AC-2.2) |
| 4 | The form's, stored and recomputed fingerprints aren't all equal | 409 with a fresh preview of the stored file and a new fingerprint (AC-3.1, AC-3.2) |
| 5 | The plan removes a lot or location and the box isn't checked | 422 "Confirm the removal to apply this file"; the upload stays (AC-3.5, AC-9.10) |
| 6 | Otherwise | writes, then 303 to the collection with the notice |

An exception in the transaction rolls everything back: 500 with a page saying nothing was changed, and the upload stays so the collector can try again (AC-2.1, AC-9.8). Two requests together: one writes, the other gets 422 or 409, never 500 (AC-2.3).

The write: removed lots are deleted; added and changed rows go in one multi-row `INSERT .. ON CONFLICT` per `BATCH_SIZE` (`Apply#upsert_lots!`, values through `?` placeholders and `sanitize_sql_array`, not `Lot.upsert_all`, whose per-value type casting took 2.6 of the 4 seconds of an apply that replaces 50,000 lots; maintainer's ruling 2026-10-24, spec 032 Phase 8) on the lot identity (`account_id`, `catalog_entry_id`, `lot_key`), setting quantity and both times, so a changed lot keeps its id. The order is: delete the removed lots (the lots of a removed location, of a removed deck's zones and of a zone a format change drops among them, so the foreign key never fires); delete the removed proxies (those of a removed deck or zone and of a zone a format change drops among them, so the cascade finds none left; spec 068 AC-7.10); write the places and decks (`CollectionImport::DeckChanges.write!`: every removal before any addition, since a place and a deck share one name space and its unique index, so a place and a deck can swap names in one file: the removed places, then the removed decks, whose zones and `decks` rows go with them by the foreign keys, and the zones the format-changed decks lose; then one upsert of the added and renamed places and one of the added and renamed decks' locations, each on the partial unique index of top-level names, `index_locations_on_account_id_and_name_key_top_level`, whose condition `WHERE parent_id IS NULL` Rails emits when the index is named and a spec reads; then one upsert of the `decks` rows of added and format-changed decks on `location_id`; and last the zone repair); read the account's places and zones once (at most 500 top-level rows, a few zones each); then upsert the lots with their `location_id` (a place resolved among places by comparison key, a zone by its (deck key, zone key) pair) and a `lot_key` that ends in it; the working state is cleared only when a lot is written; then upsert the proxies (`Apply#upsert_proxies!`: one multi-row `INSERT .. ON CONFLICT (location_id, catalog_entry_id, COALESCE(finish, ''))` per `BATCH_SIZE`, the unique index's expression, so a changed proxy keeps its id and `created_at` and a proxy with no finish is one too; the zone's id from the `[deck key, zone key]` map; the rows skip `Deck::Proxy`'s validations on purpose and a spec checks them against the model; spec 068 AC-7.10), then `collection_view` (spec 032 AC-11.1, AC-11.5, AC-11.6, research R3) (spec 028 decision 5, FR-3, FR-4, FR-9; spec 029 decision 11, FR-5). The zone repair makes every deck the file lists, changed or not, hold one zone row for each zone of its format: the zones a release added since the deck was made are inserted with the registration's key and name, and the names of the zones it has are rewritten from the registration first, in two passes (every zone to rewrite is given a name key no name can have, then its registered name), so a zone's old name never meets another's new one in the zone name index; it writes only where something differs, in a number of statements that follows the registered formats and not the decks, and it never makes a plan "something to change" on its own (spec 062 AC-8.2a, AC-8.9). The bulk statements skip `Lot`'s, `Location`'s and `Deck`'s validations on purpose, because the reader already checked each row (a deck's name's length included, AC-6.7b); specs check the written rows against the models (spec 028 FR-3, AC-2.4; spec 029 AC-9.15; spec 062 AC-8.9). Afterwards the upload's record is removed in the transaction and its blob released after it (spec 028 FR-2, decision 9; ADR 0022). The account's currency is written first in the transaction, so any later failure rolls it back with the lots (spec 038 decision 7, AC-6.9), and `replan` reloads the account inside the transaction. The notice is "Imported: N lots added, M changed, K removed", with "; 2 locations added, 1 renamed, 1 removed" for a version 2 file that changes locations and "; 2 decks added, 1 renamed, 1 format changed, 1 removed" for a version 4 file that changes decks (zero parts left out), "; 2 proxies added, 1 changed, 1 removed" for a version 4 file that changes proxies (rows, zero parts left out; spec 068 AC-7.10), then "; prices now shown in EUR" when the currency changes, and no final period (spec 028 decision 11; spec 029 AC-9.14; spec 038 AC-6.3; spec 062 AC-8.8).

### The fingerprint

It covers the stored file's checksum; the row number and outcome of every added and changed row; for every changed and removed lot its id, quantity, `created_at` and `updated_at` at full precision and its place's comparison key or, for a zone, its (deck key, zone key) pair (so a lot moved between preview and apply makes the preview stale) (spec 032 AC-11.7; spec 062 AC-7.4c); the view change; for a version 2 file, the names of added locations, the held and file names of renamed ones and the names of removed ones, with no ids; for a version 4 file, the same for decks (the names of added ones, the held and file names of renamed ones, the held and file collectible types and formats of format-changed ones, the names of removed ones, no ids), so a deck added, removed, renamed or changed in format between preview and apply makes the preview stale and a version 1 to 3 plan keeps the fingerprint it had (spec 062 AC-7.10); for a version 4 file also the proxies' part: each added row by its deck key, zone key, entry, finish and quantity, each changed row by those and both quantities, each removed proxy likewise, no id and no row number, so a proxy added, removed or changed in quantity between preview and apply makes the preview stale (spec 068 AC-7.12); and last, only when the currency changes, the account's code and the file's, so a plan without a change keeps its fingerprint and a currency changed between preview and apply makes the preview stale (spec 038 decision 7, AC-6.7). So a lot or location added, removed, edited or respelled between preview and apply, a catalog change that makes a row stop resolving, or another preview replacing the file, all change it; a location or a deck deleted and added again with the same spelling (and format) doesn't (spec 028 decision 2, AC-3.7; spec 029 decision 11, AC-9.9; full precision: spec 028 P2).

### Export or backup

An export is one collector's collection (profile, currency, locations, decks, lots), made by the collector, restorable into any instance of a release that reads its version, and replaces that collector's lots, locations and decks. A backup is the whole instance's primary and prices databases (spec 081 decision 6), made by the operator, restorable onto a fresh instance of the same or a newer release. Neither replaces the other; the 1.0 test asks for an export restored into a fresh instance, and the backup is the operator's safety. `README.md`'s "Your data" and "Export or backup?" carry the table (spec 030 decision 11, AC-6.1). Each account's currency is a column of the primary database, so a backup restores it with the account (spec 038 AC-7.1). A backup holds no Active Storage file; a restore tolerates a missing stored upload, and an apply then answers "Preview the file again." (spec 030 Active Storage row; spec 028 error scenario for a lost file). The backup restore refuses an export file and points to **Import collection** (spec 030 AC-3.3). An export holds no price: prices are global, not collector-owned data, and the export format's version is unchanged by them (spec 081 decision 4, AC-3.2).

## Decisions not in an ADR

- **Written in the request, not a job,** for the export and the apply; a job with a stored, expiring file replaces the export if 50,000 lots exceeds 10 seconds or 300 MB or a proxy times out (maintainer, 2026-10-14; spec 022 decision 1). For the apply, a missed bar needs the maintainer's ruling on a fallback (maintainer, 2026-10-20; spec 028 decision 3).
- **Applying replaces the collection;** merging was not chosen (maintainer, 2026-10-15; spec 025 decision 1).
- **A file with a problem row can't be applied, in part or otherwise** (spec 025 decision 2; spec 028 decision 4).
- **A file's currency becomes the account's** when applied; only a well-formed code outside the 20 is refused (maintainer, 2026-11-03; spec 038 decision 7, superseding spec 025 decision 3).
- **The export format kept version 3** (then the newest) when the currency moved to the account: the field's meaning didn't change (maintainer, 2026-11-03; spec 038 decision 6).
- **Only `collection_view` is taken from the profile** (spec 025 decision 4).
- **"Export collection" and "Import collection" are the first two items of the account menu and rows on More,** not in the main navigation; "Locations" is in the header and More (spec 022 decision 6; spec 025 decisions 7, 14; spec 029 decision 8). The More page's rows are Signed in as, Locations, Currency, Export collection, Import collection, Add by number, then admin links, then Sign out (`app/views/mores/show.html.erb`; Currency: spec 038 decision 4).
- **The export link is outside Turbo Drive and never prefetched** (it would build the file), and has no `download` attribute (spec 022 decision 6).
- **Signing in from the export lands on the collection** (spec 022 decision 9).
- **`generator` is left out** until the app knows its version; adding it later is information only (spec 022 decision 5).
- **Long lists show their first 100** (maintainer, 2026-10-15; spec 025 decision 11).
- **The app's rules use `json_schemer` and a byte-identical schema copy;** hand-written lot checks proved against the schema are the fallback if the time bar is missed, through an ADR that supersedes ADR 0021 (ADR 0021).
- **One-click apply from a stored upload,** with a confirmation for a removal and the export one click away; no undo (maintainer, 2026-10-20; spec 028 decisions 1, 6).
- **An apply with nothing to change is refused,** and a view-only or location-only apply clears no working state (maintainer, 2026-10-20; spec 028 decisions 7, 12; spec 029 decision 11, AC-9.17).
- **A price too large for the cents column is a problem row,** superseding spec 025 decision 9 in that point (maintainer, 2026-10-21; spec 028 1.3.4).
- **Locations in a file are normalised on read** (NFC, trimmed, collapsed) and matched by comparison key, while "the same collection" compares names as written; a name whose NFC form exceeds 60 code points refuses the file (maintainer, 2026-10-20; spec 029 decisions 9, 10; ADR 0023).
- **A file's locations replace the held ones by name;** a version 1 file leaves them alone (spec 029 decision 10).
- **A lot's location is part of its identity** (the same printing in two places is two lots), and the place is in `lot_key` as the location's id, so a rename keeps every key (maintainer, 2026-10-23; spec 032 decisions 1, 3, 7; ADR 0025). An older file's lots are read as unplaced and applying one needs the removal confirmation when it would unplace lots (spec 032 decision 7).
- **Version 3's "same collection" compares a lot's location as written,** while the reader's matching and `duplicate_lot` use the comparison key (spec 032 AC-9.6).
- **The number-entry list and the scanner sitting are working state,** left out of the export (spec 026 decision 6; the sitting's condition too, spec 042 decision 6).
- **Version 4 carries decks and a lot's zone, and a deck's zones are not listed** (maintainer D2, D3, 2026-11-10; spec 062 decision 4; ADR 0028). `decks` is a required list of `{ name, collectible_type, format }` beside `locations`, which stays the places; a lot's `location` is one field, `null`, a name or `{ deck, zone }`, with room for a later kind; the zones come from the registered format, so there is no empty-zone state to carry and a lot naming a zone its deck's format lacks is a row problem (`unknown_zone`). A deck's collectible type is in the file beside its format, so two collectibles may both have `standard` (maintainer D4).
- **Version 4 gained `proxies` before any release wrote it, so it is one version, and the list is required** (maintainer, 2026-11-11; spec 068 decision 14): a development build's (`edge` image's) version 4 file without it is refused, and an older instance reading a file with `proxies` ignores them (the format's rule for an unknown field).
- **Proxy rows are read as lot rows are** (spec 068 decision 18): one at a time against the schema, a problem a row problem, never a refusal; an apply that changes only proxies clears no working state, because no list points at proxies (spec 068 AC-7.11).
- **An older file that would collide with a held deck is refused whole** (maintainer D7, option A, 2026-11-10; spec 062 AC-7.4a, AC-7.4b, AC-7.4d): `deck_name_taken` and `too_many_with_decks`, judged again inside the apply's transaction; the apply's own writes are guarded before they run, never caught after the unique name index fails.
- **`unknown_zone` and `unknown_format` are the reader's resolvable checks,** not rules of the format (spec 062 AC-6.11; ADR 0028). A deck whose registration an instance lost still exports, and its file is refused whole as `unknown_format` on that instance, which is accepted: the file reads on any instance that has the registration.

**Accepted limits and open issues:**

- An instance that reads only version 1 can't read exports written from version 2 on (maintainer; spec 029 decision 2; ADR 0023).
- A finish a catalog refresh stops listing between resolving and writing is accepted: the lot is written (spec 028 Error Scenarios).
- On slow hardware a very large apply may hold other writes briefly; import while nothing else is writing (spec 028 decision 3; README).
- The coverage check compares names, not meaning (ADR 0020).
- A source that retires or replaces an id leaves a lot that doesn't resolve; a person repairs it by hand (ADR 0020).
- CLAUDE.md's earlier claim that no spec enforces that the location files name no collectible type is out of date: `spec/import_apply_core_spec.rb` lists them (checked on `origin/main`).
- A zone a release retires from a registration, whose name a new zone then takes, would be skipped by the zone repair's insert (it is `ON CONFLICT DO NOTHING` on the zone name index), and a lot naming the new zone would raise inside the apply's transaction: it rolls back and the collector gets the error page. Out of scope for spec 062: a release that does it needs a migration and an upgrade note (ADR 0028 Consequences).
- A deck that gains a missing zone through the repair gets it with a later id, so `Deck#zones`, which orders by id, shows it last and not in the format's order (collection and lots; matters to #253).
- A deck whose registration the instance lost can be exported but its file is refused whole by that instance (see the decisions above).
