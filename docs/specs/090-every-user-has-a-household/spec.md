## Problem Statement

Every later piece of the households lane (joining, leaving, a shared collection, transfers, borrowing) and the hosted lane's plan per household needs one fact that does not exist: which household a user, and an account, belongs to. Adding it later, after more tables exist and after more instances hold data, only gets dearer (design, "Why"). The fact has to exist for every user on every instance, including the ones that are upgraded from a release that had no households, and it has to arrive without a collector seeing anything change: no page, no word, no new rule for them to learn.

This feature adds the structure and nothing that uses it: a household with a name and its members, a role for each member, a kind for each account, a household made with every new user, and one made for every user that already exists on upgrade.

> **Terms.** *Household*: a named group of accounts; today always one user's. *Member* (of a household): a user in it. *Manager*: a member with the manager role; *plain member*: a member with the member role. *Membership*: the row that puts one user in one household with a role. *Personal account*: an account of kind `personal`, a member's own and private (what every account is today). *Shared account*: an account of kind `shared`, owned by the household and used by no single user; none exists after this feature. *Household of one*: a household with one member. **"Member" is also spec 015's word for a user without the admin flag** (the admin users page's "Member"); the two are independent: the admin flag governs the instance, the role governs a household, and no page shows a role in this feature.

## Goals

- Every user belongs to exactly one household, as a manager or a member; a household always has a manager.
- A new user, by every way a user is made (first run, sign-up, an admin, the operator's command), starts as the manager of a household of one, made in the same write as the user and their account.
- An account knows its household and its kind (`personal` or `shared`); a user's account is personal and is in the user's household.
- An existing instance gains a household for every user when it upgrades, unattended, with no row lost and no collector signed out, and the upgrade proof shows it.
- Nothing in the app looks different: no new page, link, word or field, and every tenant-isolation check passes unchanged.
- The names the later issues build on are settled here: tables, columns, roles, kinds.

## Non-Goals

- Any page, link, form or word about households: no invitation, no join or leave, no household name field, no role shown, no switch. The admin users page does not change (#389).
- A shared account, a way to create one, or a collection in it (#384). The schema allows one; nothing makes one.
- A user in two households, or a household with no member.
- Moving a user between households (#381, #382) and handing the manager role over (#383). This feature makes the rule they must keep.
- A kid role, or any role beyond manager and member (design decision 11).
- `Current.household`, or any change to how a request resolves `Current.account` (decision 14 of the design is #384's).
- Raising the export format's version or carrying a household in an export (decision 4).
- A plan, a limit or hosted mode (the hosted lane, #392 to #394).

## Users and Context

**Primary users:** every collector, who sees no change; an operator upgrading an instance, who needs the upgrade to give households to existing users with no step to run.
**Secondary users:** the agents and maintainers of #381 to #389 and #393, who build on the names and rules here; the maintainer's own instance, upgraded from the previous release.
**Usage context:** a migration at the first start after an upgrade (`db:prepare` on boot), and a household made whenever a user is.
**User mental model:** none. A household of one is invisible (design decision 10); the collector's mental model is the one they have, a private collection.

## Decisions

1. **The names.** *(Settles design decisions 10 and 11 and the schema half of 9; no departure from the design's names.)* Tables `households` (`id`, `name`, timestamps) and `memberships` (`id`, `household_id`, `user_id`, `role`, timestamps); roles `manager` and `member` (`memberships.role`, an enum with explicit values, a `CHECK` naming both); two columns on `accounts`: `household_id` (a foreign key to `households`, indexed) and `kind` (`personal` or `shared`, default `personal`, a named `CHECK`). `users.account_id` stays, unique, and `users` gains nothing. A user's household is read through their membership, an account's through `accounts.household_id`. **Both exist on purpose:** a shared account has no user, so it can't be found through a membership, and a membership is where the role lives; the cost is one fact held twice for a personal account. Its rule is decision 6.
   **Added to the design's model, each with its reason:** `memberships.user_id` is unique (one household per user, as a fact of the database, not only the model); `memberships.household_id` is indexed (the household's members are read by it). **No** index or validation about shared accounts is added: the design's "one shared account", and that a shared account has no user, are #384's to state when it makes one (a partial unique index costs no table copy later, and a model rule that a personal account has a user can't hold at the account's own insert, which comes before its user's).
   **The foreign keys' delete rules, which are schema and the dangerous part:** `accounts.household_id` → `households` is **no action** (never cascade: deleting a household must never reach an account, and through the eleven cascades a collection); `memberships.household_id` → `households` is **no action** (a household with a member can't be deleted); `memberships.user_id` → `users` is **cascade** (deleting a user removes their membership). A household that holds an account or a member can't be deleted, by the model and by the database (AC-2.9).
2. **A household of one is named for its user.** *(Ruled by the maintainer 2026-11-13, as recommended; over: a constant "Household".)* The name is stored text, the user's name followed by the straight apostrophe (U+0027) and "s household" ("Ada's household"). That suffix is 12 characters, so the user's name is cut to its **first 88 characters** and the whole is at most 100; a household's name is present and at most 100 characters. One definition builds the name for the model and for the backfill (which does it in SQL with `substr`); a spec holds the two equal on the same names (as `Location::Name`'s parity spec does), including a 100-character name, one with an apostrophe and one with multi-byte characters. It is stored, not derived, so a user's rename later changes nothing in the household, and a list of households (#389) tells them apart. No page shows or edits it in this feature; a manager renames it when a later issue gives them the page.
3. **"A household always has a manager" is enforced by the model and by the parts of the database SQLite can state.** *(Ruled by the maintainer 2026-11-13, as recommended; over: a database trigger.)* The database holds: the role `CHECK`, `memberships.user_id` unique, both foreign keys with decision 1's rules, `NOT NULL` on every column of `households` and `memberships`, and the name's length `CHECK` (decision 5 (a)). The model holds: a household is created with its first membership, a manager, in one transaction with the user; a membership can't be removed on its own (the one wording of the rule: a membership goes only with its user's delete in this feature, and the issues that let a person leave or be removed, #382 and #383, change that rule where they need to); a manager can't be demoted when no other manager remains; and a user can't be deleted when they are the last manager of a household that has other members. **No trigger:** `db/schema.rb` doesn't dump triggers, so a volume made from the schema would lack the rule that an upgraded one has. A spec and the upgrade proof check the rule on real rows (a household without a manager is a failure of both).
4. **The export does not carry the household, and the format stays version 4.** *(Ruled by the maintainer 2026-11-13, as recommended; over: carrying the name in `profile` and raising to version 5 now.)* The export is one file per account and holds the collection and its profile (design decision 16). A household is a fact about a group, not about the collection; a household of one has a default name, and a person who imports their file onto another instance is made a household there by the same rule that makes every user one. The shared collection's file and its `profile` are #384's (the design's open question 4), and that is the issue that raises the version. The format document's Coverage tables list the new data as "Left out" with the reason (`memberships`, `accounts.household_id`, `accounts.kind`); `households` has neither `account_id` nor `user_id`, so the guard doesn't ask for it, and the format document says in one sentence that the guard does not cover it and where the question is decided again (so #384 and #393 don't read the guard as covering it). The guard's own spec (`spec/export_format_document_spec.rb`) hard-codes the "Left out" tables and columns and gains `memberships`, `accounts.household_id` and `accounts.kind`; the format document's sentence that households "will raise the version (ADR 0017)" points to ADR 0030 and #384.
5. **Three migrations, as spec 049 did, all run without a transaction; the third makes `accounts.household_id` `NOT NULL` by a table copy.** *(Ruled by the maintainer 2026-11-13: (c) as written, the table copy, over the nullable fallback below, which is kept as the record of the alternative and its cost. The two conditions of the ruling: the plan review traces (c) line by line against Rails 8.1.4.1's `alter_table` and the thirteen referencing tables, and `bin/upgrade-smoke` runs from the previous release built from its tag before the push.)* All three use `disable_ddl_transaction!` and guard each step, so a run that stopped part way is finished by the next boot: (b) must, to make each batch its own short transaction (spec 049's backfill does the same), and (a) and (c) must because their `down` and (c)'s `up` copy `accounts` (below). **(c) is the exception to "guarded steps":** it wraps its stragglers step, the copy and the sequence restore in one transaction of its own, opened with enforcement already off (`disable_referential_integrity { transaction { … } }`; the copy's own inner transaction joins it), so the three commit together or not at all and a failed (c) changes nothing.
   - **(a) Schema.** Creates `households` (its `name` with a named `CHECK (length(name) BETWEEN 1 AND 100)`, as `locations_name_length` does for a location) and `memberships`; adds `accounts.household_id` and `accounts.kind` with `ALTER TABLE … ADD COLUMN`, which copies no table (a `REFERENCES` column is accepted because its default is `NULL`; a `CHECK` stated on the column is tested against every row and is kept by the schema dump when named; the precedent is `AddDecks`).
   - **(b) Backfill.** A data migration with no schema change. It reads the users that have no membership in batches of 500, and for each batch, in one short transaction, inserts a household for each user (decision 2's name), the manager membership and the account's `household_id`, with plain SQL and no application model. **The `UPDATE` of `accounts` sets `household_id` and nothing else, `updated_at` included**, because the upgrade proof compares `accounts`' rows over the columns both databases have and `expected_changes.yml` stays empty (decision 10). It is idempotent: it selects only users with no membership, so a second run, or a run that was stopped after some batches, makes exactly the rest and nothing twice; it holds no lock beyond each batch's own write transaction, so the instance's other work waits at most one batch. Cost: users, not lots; ten thousand users are twenty batches.
   - **(c) Tighten.** In one transaction (above): first runs the same idempotent backfill for stragglers (and removes a household with no member and no account, which an older container's delete of a user leaves behind: it removes the account but knows nothing of the membership the cascade already took), then makes `accounts.household_id` `NOT NULL`, then restores the `accounts` sequence as an upsert (a copy of an empty table leaves no `sqlite_sequence` row to update), so "every account has a household" is a fact of the database, as `users.account_id`'s `NOT NULL` is. **The stragglers' step matters:** (b) is recorded in `schema_migrations` once it has run and never runs again, but a user can be made between (b) and (c) (an old container still serving during a Kamal deploy, or a boot that stopped between the two), and without the step (c) would fail on every boot after. Spec 049's third migration runs the same kind of safety-net `UPDATE` before its `change_column_null`.
     **What the copy is.** SQLite can't add `NOT NULL` to a column in place. Rails (activerecord 8.1.4.1, the SQLite adapter's `alter_table`) creates a new `accounts` with the change, copies the rows, drops the old table and renames the new one, the two moves in one transaction inside `disable_referential_integrity`, so the copy itself is atomic when no outer transaction holds it. `accounts` holds one row per user, so the copy is small and short; the risk is its delete rules, not its volume.
     **What the copy risks.** `accounts` is the most referenced table in the schema: thirteen tables hold a foreign key to it. Eleven are `ON DELETE CASCADE` (`bulk_removals`, `bulk_selection_marks`, `bulk_selections`, `deck_proxies`, `decks`, `import_uploads`, `locations`, `number_entries`, `number_entry_lines`, `scanner_sitting_entries`, `scanner_sittings`), and `lots` and `users` hold SQLite's default, `NO ACTION` (`db/schema.rb`; the `RESTRICT` that makes `Account` declare `lots` before `locations`, `spec/models/account_spec.rb`, is `lots → locations`). The copy's `DROP TABLE accounts` runs an implicit delete of every row, so with foreign keys enforced: the eleven cascades **delete every collector's decks, places, proxies and working state, silently**, and `lots` and `users` are deferred to the end of the transaction rather than refused. Rails turns enforcement off for a copy only **outside a transaction** (`PRAGMA foreign_keys = OFF` does nothing inside one, and Rails then defers the keys), so a copy that ran inside Rails' own migration transaction would lose that data with no error. That is why (c) runs without Rails' migration transaction, and opens its own with enforcement already off: outside any transaction the steps would each commit alone, and a (c) that stopped after the copy and before the sequence's restore would never get it back, since the next boot finds the column already `NOT NULL`. **Two more effects the proof must catch:** the copy drops and recreates the table, so the `sqlite_sequence` row for `accounts` restarts at the highest id present, and an id of a deleted account can be reused (`compare.rb` skips `sqlite_%` tables, so the proof can't see it: (c) reads the sequence before the copy and restores it after, in the same transaction, and AC-3.6 asserts it); and an older release's image started on the upgraded volume can't create a user or account any more, since it doesn't know the column (the same of every added `NOT NULL` column). **Collector documents no downgrade:** the README says to back up before every upgrade, and going back means restoring that backup onto a new volume under the old image and losing what was written since; `docs/releasing.md`'s Upgrade notes carry this migration's warning. Also: **a failed (c) stops the boot** (Compose is down until it is fixed; Kamal keeps the old container serving), and during a Kamal deploy an old container's sign-up or add-a-user fails with a 500 for the seconds between (c) and the switch. The precedent is narrower than a pattern: the one shipped copy of a referenced table by an `up` is `sessions` (spec 049), with two cascading children against thirteen here; `AddDecks` and its kin add columns without a copy.
     **What proves no row is lost.** The upgrade proof compares every table of the old database with the upgraded one over the columns both have, row by row (`script/upgrade/compare.rb`), and its seed holds a row in every table, including each of the thirteen; `PRAGMA foreign_key_check` and `integrity_check` run on the result; a migration spec runs (c) on a database holding rows in each referencing table and asserts every count, and the `accounts` sequence, is unchanged; and the copy's foreign keys, named checks and indexes are read back against the schema dump. The same holds for (c)'s and (a)'s `down`, which also copy `accounts` (AC-3.5).
   - **The nullable fallback (a real option).** Skip (c): `accounts.household_id` stays nullable in the database and the model validates it present. *Gains:* no copy of `accounts`, no sequence to restore, no step that can stop a boot, and nothing in this feature can lose a row; (a)'s `down` still copies `accounts`, once. *Costs:* an older image on an upgraded volume (the Kamal deploy window) still creates users, **each with no membership and an account with no household, and nothing ever repairs it, because (b) is recorded and never runs again**: under the fallback the Goal "every user in exactly one household" can be broken permanently by one deploy. To be sound the fallback needs a repair that runs on every boot (the stragglers step run from `db:prepare`'s boot path) or a household made on first load; neither is in this spec, so the fallback as written does not meet the Goal. The database also can't state "every account has a household", so a bug or a hand-written insert can leave an account with none, and only a guard spec and the upgrade proof would notice; and a fresh volume (built from `schema.rb`) and an upgraded one agree only while the column is nullable in both, so the schema says nullable until a later migration pays the copy then, with more tables referencing `accounts` and more instances to carry through it (the design's own reason for doing this now). **The same under both options:** a fresh volume loads `db/schema.rb` and runs no copy; an older backup restored is migrated like an upgrade; a backup taken after the upgrade is refused by the older release either way. The recommendation is (c), for those costs and because the proof that guards it exists and this issue is the cheapest time to pay it; but the copy is the one step of this feature that can lose data if its guard is wrong, and the maintainer rules between them. If the plan review's trace finds (c) unsafe, the maintainer is asked again before the fallback is taken, and this spec's version records the outcome.
   - **Reversible:** (c)'s `down` makes the column nullable again by the same copy, restoring the sequence as its `up` does; (b)'s `down` does nothing (a second run of its `up` finds nothing to do); (a)'s `down` drops the tables and the two columns (the `kind` check before its column, as `AddDecks`' `down` does, so (a)'s `down` copies `accounts` three times (the check's removal, `kind`'s and `household_id`'s) and a full rollback four times with (c)'s), keeping the sequence at each copy and **refuses**, with an `IrreversibleMigration` that says what exists, when any household has more than one member or any shared account exists, since the older code can't hold either; a household of one is removed with its name.
6. **A personal account is in its user's household.** For a user, `accounts.household_id` of their account equals `memberships.household_id` of their membership. The database can't compare two tables, so the rule is the model's (a user is built with both from one household; a later issue that moves a user changes both in one transaction), and a guard spec and the upgrade proof check it on real rows. A shared account has no user; a personal account has exactly one.
7. **Deleting a user removes their membership, their account, and, when no one is left, their household.** An admin's delete of a user (spec 004 AC-5.4) works as before. The order is the foreign keys': the user's row (its membership goes with it by decision 1's cascade, **without** the membership's own refusal of decision 3, which guards a membership removed on its own; the user's delete has its own check for the last manager), then the account (`User` declares `belongs_to :account, dependent: :destroy`), then the household when no member and no account is left. A household left with other members keeps them, and the model refuses the delete when the user is the household's last manager and others remain (no page makes such a household in this feature, so only a model spec reaches it; #382 and #383 give it a page and a message). The removal of a household "when no member and no account is left" is revisited by #381 (a joiner leaves a household of one behind) and #384 (a shared account is an account of the household).
8. **A household is made by the user model, so every path gets one.** The one place an account is made from a user today (`before_validation :build_account`) also makes the household and the manager membership; the first-run sign-up, the open sign-up, the admin's add-a-user form and `bin/rails collector:user` all go through it, and a spec per path says so. Nothing in a request names a household, a role or a kind (`household_id`, `role` and `kind` are not permitted from parameters).
9. **"Nothing looks different" is checked by five things, beyond the existing specs passing unchanged.** (i) A request spec renders the collection, the admin users page, the account menu, sign-in, sign-up and the catalog search as a collector and as an admin and asserts that none of the bodies contains "household" (case-insensitive), and counts the queries of those requests that name `households` or `memberships` (none). (ii) The existing tenancy request specs and system specs are not edited, except where they build a user by hand (the factory makes the household), and the run proves they pass. **The allowed edits to the suite's support code:** `factory :account` (used by `spec/models/account_spec.rb`, `spec/helpers/scanners_helper_spec.rb` and `spec/lib/collector/scanner_findings/art_sitting_report_spec.rb`) gains a household, a bare one with no member (those examples have no user, and the helper of AC-2.8 isn't called after them); and the two places that insert an account by SQL (`spec/support/backup_helpers.rb`, `spec/lib/collector/backup/snapshot_spec.rb`) insert a household first. Nothing else in `spec/` changes for the tenancy checks. (iii) `bin/rails routes` on the branch and on `main` before it are compared once, at the implementation review, and the empty diff is recorded in `verification.md` (no permanent route-list spec: it would conflict with every branch that adds a route). (iv) A one-off search of `app/views`, `app/helpers`, `app/controllers`, `app/javascript` and `config/locales` for "household" and "membership" finds nothing outside the models, recorded beside the routes diff. (v) The upgrade proof's web leg (spec 031 Story 5) signs in as each seeded user on the upgraded instance and loads the collection, locations and export pages, as it does today, and that leg runs after the backfill.
10. **The upgrade proof gains a household check in two tiers, and `expected_changes.yml` stays empty.** *(Ruled by the maintainer 2026-11-13, as recommended.)* `compare.rb` reads only the old database's tables and the columns both databases have, so the new tables and columns are invisible to it and no entry would match; the harness gains a check on the snapshots it takes. **Tier 1, always** (it must stay true when #381 and #384 add joined households and shared accounts, so it names no count): every user has exactly one membership, every household has at least one manager, every account has a household, and a personal account's household is its user's. **Tier 2, only when the old snapshot has no `households` table** (the backfill's own facts): the households' count equals the users' (the seed's two users make two), every membership is `manager`, every account is `personal`, and every household's name is its user's name's form of decision 2. Tier 1 runs on the upgraded snapshot, on the restore leg's, and on the `next` snapshot of a fresh instance of the code under test (`next_release`), the one place the production image's creation path is proved. The seed for the next release (`script/upgrade/seeds/next.rb`) creates its users through the models, so the new tables hold rows, as the seed rule needs.
11. **The ADR is 0030, proposed with the pull request (the maintainer accepts it), and the area docs change with it.** [ADR 0030](../../adr/0030-a-household-is-a-group-of-accounts.md) supersedes the one-user half of ADR 0017 (an account may now be one of several in a household, `users.account_id` stays unique, an account stays the unit of ownership and privacy) and keeps the rest of ADR 0017 (the `account_id` rule, `Current.account`, 404 for another account's record). ADR 0017 has a status line saying it is superseded in part; its one-user text isn't rewritten; ADR 0030 stays Proposed in this pull request: the maintainer's ruling on its decisions is recorded in it, and accepting the ADR itself is theirs, recorded in the plan-retirement pull request as for ADR 0029. The docs that change: [`tenancy-and-accounts.md`](../../architecture/tenancy-and-accounts.md) (glossary, invariants, the delete, accepted limits, and a line that `households` and `memberships` are instance-level tables never scoped through `Current.account`), [`.claude/rules/multi-tenancy.md`](../../../.claude/rules/multi-tenancy.md) (the same line), [`data-portability.md`](../../architecture/data-portability.md) and the [export format](../../export-format/README.md) (coverage, decision 4, and the sentence at its version history), [`release-and-deploy.md`](../../architecture/release-and-deploy.md) (the harness's check), `docs/releasing.md`'s Upgrade notes (the migration's entry and warning), the [specs index](../README.md) (this spec's row and spec 004's, both directions), and `CLAUDE.md`'s Project Status paragraph.
12. **Hosted-door rules.** *Cost per household:* one household row, one membership row per member, no row per lot or per request. *Stored per account or user:* the household's name and members' roles are the household's, nothing else is stored about a collector's choices. *The operator is not the user:* no admin page changes, so none shows a collection; the household's fields are not on any page.

## User Stories and Acceptance Criteria

### Story 1: A new user starts in a household of one

**As** an operator or a person signing up **I want** every user, however they are made, to be the manager of a household of one **so that** the later features have a household to work with from the first day.

- [ ] **AC-1.1** Given an instance with no user When the first visitor signs up Then a user, their personal account, a household named "<name>'s household" and a membership with role `manager` exist, the account's household is that household, and the page the visitor lands on is the collection as before.
- [ ] **AC-1.2** Given sign-up is open When a person signs up Then they have the same four records, as the manager of a household of their own (not the first user's).
- [ ] **AC-1.3** Given an admin on the users page When they add a user Then the user has the same four records, and the admin's own household is unchanged.
- [ ] **AC-1.4** Given the operator's command When it creates an admin by email Then the admin has the same four records.
- [ ] **AC-1.5** Given a user whose name is 100 characters When the user is created Then the household's name is exactly the user's first 88 characters followed by "'s household" (100 characters); given a name of one character Then it is that character followed by "'s household"; and the backfill's SQL builds the same name as the model for a 100-character name, a name with an apostrophe and a name of multi-byte characters.
- [ ] **AC-1.6** Given a sign-up that is invalid (a blank name, a used email) When it is submitted Then no household, membership or account exists afterwards, and a sign-up that loses the first-user race (spec 004 AC-3.4) leaves none either.
- [ ] **AC-1.7** Given any request that creates a user When its parameters hold `household_id`, `role` or `kind` Then they are ignored: the user's household is a new one, their role `manager` and their account `personal`.

### Story 2: The rules of a household hold

**As** a maintainer of the later households issues **I want** the structure to refuse what a household may not be **so that** a bug in a later page can't leave a household without a manager or a user in two.

- [ ] **AC-2.1** Given a membership When its role is anything but `manager` or `member` Then the model refuses it, and an insert that bypasses the model is refused by the database.
- [ ] **AC-2.2** Given a user with a membership When a second membership is made for them, in the same or another household Then the model refuses it, and an insert that bypasses the model is refused by the database.
- [ ] **AC-2.3** Given a household with two members, one a manager When the manager's role is changed to member, or their user is deleted Then it is refused and nothing changes; given the same household with two managers When one is demoted Then it succeeds.
- [ ] **AC-2.4** Given any membership, a household of one's included When it is removed on its own, through the model, Then it is refused; the only way a membership goes in this feature is with its user's delete (AC-4.4), which for a household of one removes the household too.
- [ ] **AC-2.5** Given an account When its kind is anything but `personal` or `shared` Then the model refuses it and the database refuses a bypassing insert. No shared account exists in any request or in the seed, and no index or validation about one is added (decision 1).
- [ ] **AC-2.6** Given a user whose account is in a different household from their membership's When the user is validated Then it is refused (decision 6); given a user built through the model Then the two households are the same one.
- [ ] **AC-2.7** Given a household name that is blank or over 100 characters When it is saved Then the model refuses it, and an insert that bypasses the model is refused by the database's named `CHECK`.
- [ ] **AC-2.8** Given a spec helper that checks the invariants on the test database (each user has exactly one membership, each household has a manager, each account has a household, each personal account's household is its user's) When it is called after the examples that make users by each of the four paths of Story 1, delete a user and apply an import Then it passes each time (the same invariants as the upgrade proof's tier 1, decision 10).
- [ ] **AC-2.9** Given a household that holds an account or a member When it is destroyed through the model, or its row is deleted by a statement that bypasses the model Then it is refused and no account, membership or collection row changes (decision 1's no-action keys).

### Story 3: An existing instance gains households on upgrade

**As** an operator **I want** every existing user to have a household after the upgrade **so that** nothing breaks and nothing is left for me to do.

- [ ] **AC-3.1** Given a database as the previous release leaves it (users, accounts, lots, locations, decks, proxies, sessions, working state, the prices database untouched) When the migrations run Then every user has one household named "<name>'s household", one membership with role `manager`, and an account whose household is it, every account kind is `personal`, and the rows of every old table are unchanged, `accounts.updated_at` included (the backfill sets `household_id` only).
- [ ] **AC-3.2** Given the migrations have run When the backfill runs again (its migration is applied a second time, or the database is migrated from a state with some users done) Then no household or membership is added or changed and the count of each is the same.
- [ ] **AC-3.3** Given 1,201 users with no membership When the backfill runs Then it makes households in batches of at most 500, each batch one transaction, and every user has exactly one household afterwards; given it stops after the first batch When the migrations run again Then the rest are made and the first batch's are not made twice.
- [ ] **AC-3.4** Given an instance with no users When the migrations run on an empty database Then they succeed and the first sign-up gets its household by AC-1.1; and a database made from `db/schema.rb` (a fresh volume) and one migrated while empty have the same `accounts`, `households` and `memberships` columns, foreign keys, checks and indexes as read by `PRAGMA` (not as the table's SQL text, which a column-level check before a copy and a table-level one after it state differently).
- [ ] **AC-3.5** Given the three migrations have run on a database that holds rows in every table that references `accounts` When they are rolled back Then the database has the schema before (a) and the count of every one of those tables, every old row and the `accounts` sequence are unchanged; given a household with two members or a shared account When (a) is rolled back Then it refuses, names what exists, and changes nothing.
- [ ] **AC-3.6** Given (c) has run on a database that holds rows in every table that references `accounts` When the counts are compared before and after Then each is equal, the `sqlite_sequence` row of `accounts` is unchanged (a new account after (c) gets an id above the highest ever issued, not a reused one), `PRAGMA foreign_key_check` and `integrity_check` report nothing, and the foreign keys, named checks and indexes of `accounts` and of its thirteen referencing tables are those of the schema dump; given the copy raises part way (a fault injected after the stragglers step) Then `accounts`, the thirteen tables, the households and the sequence are as before (nothing committed) and a second run succeeds. The example runs `:committed` through the migrator outside any example transaction (inside one, enforcement stays on and the cascades fire), as `spec/migrations/add_currency_to_accounts_spec.rb` does.
- [ ] **AC-3.7** Given a user made after (b) has run and before (c) When (c) runs Then the user is given a household by (c)'s stragglers step and (c) succeeds; given a household left with no member and no account by an older container's delete of a user Then (c) removes it; given (c) is run again Then it changes nothing.
- [ ] **AC-3.8** Given sessions exist before the three migrations run When they have run Then every `sessions` row is unchanged, so a collector signed in before the upgrade is still signed in (spec 049's rule for upgrades; the upgrade proof's behaviour leg signs in with the old password and checks the same).

### Story 4: Nothing looks different

**As** a collector **I want** the app to be exactly what it was **so that** nothing I do or see has to be learned again.

- [ ] **AC-4.1** Given a collector and an admin When each opens the collection, the admin users page, the account menu, sign-in, sign-up and the catalog search Then no body contains "household" (case-insensitive), and each page's status and text equal what they were on `main` before this feature (the existing specs for each, unedited, pass).
- [ ] **AC-4.2** Given the application's routes When `bin/rails routes` on the branch is compared with the output on `main` before this feature Then the diff is empty (checked once at the implementation review and recorded in `verification.md`; not an RSpec example, decision 9).
- [ ] **AC-4.3** Given every existing request spec for another account's record When the suite runs Then each passes unchanged: another account's record is 404, and `Current.account` is still the signed-in user's own account.
- [ ] **AC-4.4** Given an admin deletes a user (spec 004 AC-5.4) When it completes Then the confirmation, the notice and the other accounts are as before, and the deleted user's household, membership and account are gone.
- [ ] **AC-4.5** Given the pages of decision 9 (i) When each is requested Then no query of the request names `households` or `memberships`, and the admin users page's rows, counts and buttons are as before.

### Story 5: The export and the backup stay whole

**As** a collector **I want** my export to round-trip and my instance's backup to keep working **so that** nothing about my data's safety changes.

- [ ] **AC-5.1** Given the export format document When its Coverage tables are compared with the database Then `memberships` is a table "Left out" with its reason, `accounts.household_id` and `accounts.kind` are columns "Left out" with their reasons, `households` is not a row (it has neither `account_id` nor `user_id`), the guard's own spec lists the three additions, the guard passes, and no new field is in the schema or the examples; the format version stays 4.
- [ ] **AC-5.2** Given a collector's export When it is applied to the same account, or to a fresh user's account on a fresh instance Then the lots, locations, decks, proxies and currency round-trip as before, and the account's household, membership and kind are unchanged by the apply.
- [ ] **AC-5.3** Given `backup:create` and `backup:restore` When they run on an instance that has households Then the restored instance has the same households and memberships (they are in the primary database, which the backup holds whole), and `spec/backup_guards_spec.rb` passes unedited.

## Functional Requirements

### FR-1: The household structure

A household has a name; a membership puts one user in one household with a role; an account has a household and a kind (decisions 1, 2, 6).

**Must:** keep `users.account_id` unique; keep every `account_id` rule of ADR 0017; give each personal account exactly one user; keep a shared account out of every request and every seed.
**Must not:** add a column to `users`; read or write a household in any controller, view or helper; add `Current.household`.

### FR-2: Every user is made with their household

The user model makes the household, the manager membership and the account together, in the transaction that saves the user (decision 8).

**Must:** work for the four paths of Story 1; roll back with the user; take the household's name from decision 2.
**Must not:** accept a household, role or kind from a request; make a household for a user who already has one.

### FR-3: The migrations

Three migrations, in the order of decision 5.

**Must:** run unattended from the previous release and from any older one; be guarded so a stopped run is finished by the next boot; run all three without a transaction (decision 5); give a user made between (b) and (c) a household before (c) tightens; keep `accounts`' id sequence across the copy; touch no table the previous release's code reads other than `accounts`.
**Must not:** edit a released migration; reference an application model; sign anyone out; write a row per lot, per location or per request.

### FR-4: The upgrade proof

The harness checks the upgraded and the restored snapshots (decision 10).

**Must:** fail naming the broken rule; check tier 1 always and tier 2 only on a backfill (decision 10); leave `expected_changes.yml` empty.
**Must not:** weaken a comparison of an old table.

### FR-5: Documentation

The ADR (proposed, with the maintainer's rulings on its decisions), the tenancy area doc, `.claude/rules/multi-tenancy.md`, the format document's Coverage and sentences, the release-and-deploy area doc's upgrade-proof paragraph, `docs/releasing.md`'s Upgrade notes (this migration's entry and its warning), `CLAUDE.md`'s Project Status line for accounts, the specs index in both directions (decision 11).

**Must:** record the supersession in this spec, ADR 0030 and the index in both directions (`.claude/rules/documentation.md`).
**Must not:** rewrite ADR 0017's text, or restate an area's rules in `CLAUDE.md`.

## Non-Functional Requirements

### Performance

- The backfill's batch is a short write transaction, so another request waits at most one batch's write; on 10,000 users it makes 20 batches and completes in seconds (measured by a `timing: true` example on the plan's larger count, not asserted as a hard bound).
- A request's queries are unchanged: no request reads a household. A new user costs two extra inserts (household, membership).

### Security

- `household_id`, `role` and `kind` are never permitted from parameters. Another account's record is still 404; no household rule gives one user a view of another's collection.
- The admin gate and the admin pages are unchanged; no admin page shows a household, a role or a collection.
- No migration, spec or seed runs the `sqlite3` command or a production-environment task.

### Reliability

- A migration that stops part way is finished by the next boot (guards, idempotent backfill); a failed (c) leaves `accounts` as it was or finished, never missing rows (AC-3.6, AC-3.7).
- A restore of an older backup is migrated by the same migrations (AC-6.2's restore leg).

## Error Scenarios

| Scenario | Expected Behavior |
|----------|-------------------|
| A user is created and the household or membership insert fails | The whole write rolls back; no user, account, household or membership remains; the sign-up or admin form shows the error it shows for any failed save |
| The backfill is stopped after some batches | The next boot's migration makes the households of the users that have none and no other; no user has two |
| The backfill meets a busy database | A batch's transaction waits on the busy timeout as every write does; a failure ends the migration, and the next boot resumes it |
| (c) fails (a fault, a busy database past its timeout) | Nothing changed: its stragglers step, copy and sequence restore are one transaction, so the next boot runs it whole; the boot stops until it does (Kamal keeps the old container) |
| An older container sign-up or add-a-user after (c) | Fails with a 500 until the switch; documented in the Upgrade notes |
| (a) is rolled back with a two-member household or a shared account | Refused: "N households with more than one member and M shared accounts exist; remove them before rolling back"; nothing changes |
| An admin deletes the last manager of a household with other members | Refused by the model; no page makes such a household yet (#382, #383) |
| A restored backup from before this feature | Migrated at the next start like an upgrade; households exist for every user |
