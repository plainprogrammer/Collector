# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Status

Collector is a self-hostable, multi-tenant web app for tracking collectibles, starting with Magic: The Gathering cards. The Rails app skeleton exists (stack, RSpec, `bin/ci`, Compose and Kamal deployment). Feature 002 added a collectible-agnostic catalog core (`app/models/catalog/`) with an MTG extension (`app/models/mtg/`), Scryfall bulk-data ingestion via a background refresh, and a card search at `/catalog/entries`, which has needed sign-in since accounts (spec 004) unless the operator opens it with `COLLECTOR_PUBLIC_CATALOG` (spec 023). Accounts (row-level tenancy through `Current.account`) and collections of lots (spec 004, list view spec 006) exist, and the card scanner (specs 005, 007–009) adds scanned cards to the collection through its confirm flow. Admins start and watch catalog refreshes and art index builds at `/admin/catalog`, and see, retry and discard background jobs at `/admin/jobs` (spec 015). A collector's data has a documented export format, and a collector downloads, previews and applies an export file from the account menu or More (`CollectionExport`, `CollectionImport`, `CollectionImport::Apply`; [`docs/architecture/data-portability.md`](docs/architecture/data-portability.md)). A collector adds cards from a set by collector number at `/collection/number_entry` ("Add by number", spec 026): one line per number, quantity and finish, each added at once to a per-account list with Undo (`NumberEntry`, `NumberEntry::Line`), which Done clears; the list is working state, left out of the export. A collector manages the places their collection is kept in at `/locations` (`Location`, spec 029) and records which location a lot is in when adding or editing it, or moves some or all of a lot's copies with Move copies (`Lot::Move`, spec 032; a location that holds copies can't be removed; export format version 3) and moves every copy of many lots at once from bulk mode with Move to… (`Lot::BulkMove`, spec 041), opens a location's lots in bulk mode from its removal refusal page with one button (`Locations::SelectionsController`, spec 059), and the collection's grid tiles and table rows show it (spec 033) and filter by it (spec 037). A collector creates, renames and removes decks at `/decks` (`Deck`, `Deck::Creation`, `Catalog::Formats`, spec 062, [ADR 0028](docs/adr/0028-decks-are-locations-with-zones.md)): a deck is a location of kind `deck` whose zones are child locations that hold its copies, the collectible extension registers the formats, a lot in a zone is shown as "Deck › Zone", and the export format (version 4) carries decks. An operator backs up a running instance and restores it onto a fresh volume with two rake tasks, `backup:create[DIRECTORY]` and `backup:restore[FILE]` (`Collector::Backup`, `lib/collector/backup/`, spec 030, ADR 0024). CI proves an upgrade from the previous release's published image (`bin/upgrade-smoke`, `script/upgrade/`, spec 031, #42; [release and deploy](docs/architecture/release-and-deploy.md)). License: AGPL-3.0.

Mission and principles: `.claude/memory/foundation.md`. Goal and spec rules: `docs/north-star.md`. Order of work: `docs/roadmap.md`. Decisions: `docs/adr/` (index in its README). Current rules per subsystem: `docs/architecture/` (area docs). Detailed coding rules: `.claude/rules/`. Feature specs: `docs/specs/` (index: `docs/specs/README.md`).

## Stack

Ruby 4.0.7, Rails 8.1.4, SQLite in every environment (including production), Hotwire (Turbo + Stimulus), Propshaft + importmap (no Node toolchain), Solid Queue / Solid Cache / Solid Cable, RSpec + FactoryBot + Capybara, WebMock/VCR, RuboCop (`rubocop-rails-omakase` + `rubocop-rspec`), Brakeman, bundler-audit, Kamal 2.12.0.

## Commands

- Setup: `bin/setup` (idempotent; works in clones and worktrees, copies `.worktreeinclude` files from the main checkout, enables `.githooks/` auto-setup; starts the server afterwards, `--skip-server` to not)
- Run: `bin/dev` (just `bin/rails server`; port 3000, or the worktree's port printed by `bin/setup`)
- All specs: `bin/rspec`
- Single spec file / example: `bin/rspec spec/requests/health_check_spec.rb:5`
- Lint (autocorrect): `bin/rubocop -a`
- API docs: `bin/yard doc` (spec 054, ADR 0027) writes the browsable site to `doc/` (ignored by Git, left out of the image): the classes of `app` and `lib` from their comments, with the area docs and ADRs as pages and the area map as the front page. A YARD warning, such as an unresolved `{…}` in a comment, fails it, and fails the `bin/ci checks` step "Docs: YARD builds without warnings". What to write in comments (the why, reusable code, extension contracts) is in `.claude/rules/code-documentation.md`.
- Security: `bin/brakeman`, `bin/bundler-audit`, `bin/importmap audit`
- Local CI (single CI definition, `config/ci.rb`): `bin/ci` — setup, migration guard, RuboCop, YARD, the comment ratchet (spec 056: public code the branch adds or changes needs a summary; `.claude/rules/code-documentation.md`), Brakeman, bundler-audit, importmap audit, RSpec, serially. Groups (spec 035): `bin/ci checks` (everything but RSpec), `bin/ci rspec` (setup and the whole suite), `bin/ci rspec N/M` (shard N of M as GitHub runs it, to replay a failed shard; it prints a `CI=true bin/rspec --seed …` command for the same files, order and seed). GitHub Actions runs `bin/ci checks` and the RSpec shards in parallel, then builds, smoke-tests and publishes the container image; the rules are in [release and deploy](docs/architecture/release-and-deploy.md) (procedures: `docs/releasing.md`). Change CI steps in `config/ci.rb`.
- Shards' run-time log: `script/ci/record_runtime_log` rewrites `spec/support/runtime_log.txt` from a serial run; when to refresh it is in the area doc above. It runs the suite, so not while another run uses the worktree's test database.
- Backup smoke: `bin/backup-smoke <image> [restore-image]` (spec 030): backs up a running container and restores it into a second one under another secret, the documented ways; CI runs it after `bin/image-smoke` on both architectures; it needs a container engine, so it is not a `bin/ci` step.
- Upgrade smoke: `bin/upgrade-smoke <previous|auto> <current>` (spec 031): boots the previous release's published image, seeds it, starts a build on the same volume and compares the databases and what the app serves; CI runs it in the image job, before the push, on both architectures; it needs a container engine and a Ruby with the bundle, so it is not a `bin/ci` step. `ruby script/upgrade/guard.rb` is a `bin/ci` step.
- DB: `bin/rails db:prepare` (also what containers run on boot via `bin/docker-entrypoint`)
- Catalog: `bin/rails "catalog:refresh[mtg]"` (queues a background refresh), `bin/rails "catalog:status[mtg]"` (10 most recent runs); extra languages via `COLLECTOR_MTG_LANGUAGES`
- Containers locally: `docker compose up -d` (the dev machine runs Docker, not Podman; `compose.yaml` needs `SECRET_KEY_BASE`, optional `COLLECTOR_PORT`)

## Non-obvious Facts

- **Dev mirrors prod.** Development uses separate SQLite DBs (`storage/development{,_cache,_queue,_cable}.sqlite3`) and runs Solid Queue inside Puma (`config/puma.rb` plugin), so the server already processes jobs. Never also run `bin/jobs` (two supervisors on one SQLite queue DB). The test env uses Rails defaults (primary DB only, `:test` job adapter, null cache); Solid Queue's tables are loaded into that one database for the admin pages' specs.
- **Worktrees:** `bin/setup` sets `core.hooksPath=.githooks` (unless a custom hooks path exists), so `git worktree add`, `claude --worktree` and Orca (`orca.yaml`) worktrees set themselves up via `.githooks/post-checkout` (new linked worktrees only; failures keep the worktree). Each worktree has its own DBs; dev port is 3000 in the main checkout, 3001–3999 per worktree (`lib/collector/dev_port.rb`), `PORT` overrides. Setup (`orca.yaml`, the hook) runs through `script/worktree/with_mise`, which finds mise even off the `PATH` and drops mise's own directories from it so `mise exec` puts them first: Orca's setup shell is a login `bash` that may have only `/usr/bin:/bin:/usr/sbin:/sbin` and no mise, or mise's directories behind `/usr/bin`'s Ruby 2.6 (#225, #268). Copy list = `.worktreeinclude` (copied only if missing, mode 0600; logic in `lib/collector/worktree_setup.rb`). A missing `config/master.key` only warns; a wrong one breaks boot.
- **Specs:** tag spec types explicitly (`type: :request`, `type: :system`; no inference); multi-expectation examples use `:aggregate_failures`. System specs run in headless Firefox. WebMock + VCR block all real HTTP (cassettes in `spec/cassettes`).
- **Release and deploy (specs 001, 012, 013, 020, 030, 031, 035; ADRs 0008–0011, 0022, 0024):** the image, the CI groups and shards, the CI publishing, release tags, the registry cleanup, the Compose and Kamal paths, the 40 MB request body limit, the stored import upload's retention, backup and restore, and the upgrade proof and its release steps are in [`docs/architecture/release-and-deploy.md`](docs/architecture/release-and-deploy.md) (procedures: `docs/releasing.md`, `docs/backup-restore.md`). Before touching a deployment file: `README.md` documents both paths and must stay in sync; the image is public, so `.dockerignore` keeps development files out of it and `bin/image-smoke` guards that; deploy a release with `bin/kamal deploy --skip-push --version X.Y.Z`, never a plain `bin/kamal deploy`.
- **Catalog core (specs 002, 016, 018, 019, 023; ADRs 0003, 0018):** catalog data is global (no `account_id`), changes only through a refresh or the art build, and pages never call Scryfall during render. The records, source contract, name index, search, card and printings pages, footer notice, image fit and the open catalog are in [`docs/architecture/catalog-core.md`](docs/architecture/catalog-core.md); the refresh and the art build are in `catalog-operations.md` below.
- **Admin catalog and jobs (specs 015, 024, 055; ADRs 0014, 0015):** the refresh and art build lifecycles, stall and interrupt rules, rate-limit retries, "Retry now" for a waiting retry and the `/admin/catalog` and `/admin/jobs` pages are in [`docs/architecture/catalog-operations.md`](docs/architecture/catalog-operations.md). In specs, tag an example `:solid_queue` to queue through Solid Queue (no worker runs) and move jobs with `queue_job`, `claim_job`, `fail_job`, `finish_job`.
- **Footer and open catalog (specs 018, 023):** the footer's lines come from each source's `.content_notice` and core code never names a collectible (`spec/footer_core_spec.rb`). `Catalog.public?` is the one test of `COLLECTOR_PUBLIC_CATALOG`, never read from the environment in tests (tag an example `:public_catalog`); views use `collector?`, never the setting. Rules: [`catalog-core.md`](docs/architecture/catalog-core.md).
- **Active Storage variants (spec 014, ADR 0013)** use libvips through `ruby-vips`, which is bundled with `require: false` so the app boots without libvips (it then logs "requires the ruby-vips gem"). Development needs libvips (`vips` on Fedora, `libvips` on Debian/Ubuntu): `bin/setup` prints a hint when it's missing (`Collector::LibvipsCheck`), CI installs it, and `bin/image-smoke` fails an image whose variant transformer isn't vips. The only Active Storage upload is the import preview's stored file (`ImportUpload`, spec 028, ADR 0022), which meets ADR 0013's owed validation for itself (content type by content, size; no pixels, it is no image); pixel limits stay with the first image upload. Active Storage's routes are gated app-wide by `ActiveStorageGate` (`config/initializers/active_storage_gate.rb`): sign-in, ownership of original blobs only, and 404 for direct uploads and the disk service's upload PUT until a feature needs them; the first image feature extends ownership to variants and previews (ADR 0022).
- **Card scanner (specs 005, 007–011, 040, 042, 047):** `/scanner`, linked from the navigation ("Scan") and the collection page. How it reads a card, ranks candidates (with the optional art match), adds a copy, keeps the sitting with its condition and place, and records findings is in [`docs/architecture/scanner.md`](docs/architecture/scanner.md). Before you look: the OCR engine is fetched and checksum-verified into the ignored `vendor/ocr/v7.0.0/` by `bin/fetch-ocr-engine` (run by `bin/setup` and the Dockerfile), and scanner specs fail until it's installed; art matching (opt-in, `COLLECTOR_MTG_ART_MATCHING`) needs ImageMagick (`magick` or `convert`) for its build and specs; only scanner pages send a Content-Security-Policy (`ScannerPage` concern); the sitting's files name no collectible (`spec/scanner_sitting_core_spec.rb`); `script/scanner/detector_parity.rb` checks the detector (`app/javascript/scanner/detector.js`) against the spike's; measurement mode (`/scanner/measurement`, with the `scanner:` rake tasks and `script/scanner/` for the findings) is development-only (`config.x.scanner_measurement`; `COLLECTOR_SCANNER_MANIFEST`, `COLLECTOR_SCANNER_RUN_DIR`, `COLLECTOR_SCANNER_KEEP_FRAMES=1` keeps live frames) and writes outside the repo; the spikes are in `spikes/card_scanner/`. Phones need HTTPS: `bin/dev-certificate` makes a self-signed certificate outside the repo and prints the `bin/dev -b "ssl://…"` bind (alternative: a tunnel with `RAILS_DEVELOPMENT_HOSTS` + `COLLECTOR_HTTPS=true`).
- **Export format and import (specs 017, 022, 025, 028, 032, 062; ADRs 0020–0023, 0025, 0028):** the current rules are in [`docs/architecture/data-portability.md`](docs/architecture/data-portability.md); the format is defined by `docs/export-format/README.md`. Version 4 is current (`ExportFormat::Rules::VERSIONS` is `[1, 2, 3, 4]`); a new table with `account_id` or `user_id`, or a new column on `accounts`, `lots`, `users` or `locations`, fails the suite until the document's Coverage tables list it; a new field of collector-owned data raises the version.
- **Import preview and apply (specs 025, 028):** area doc above. The stored upload's retention and sweep (`ImportUpload`, `ImportUpload::SweepJob`, ADR 0022) and the 40 MB request body caps (Puma, `MAX_REQUEST_BODY` in the `Dockerfile`, `config/deploy.yml`) are in [`docs/architecture/release-and-deploy.md`](docs/architecture/release-and-deploy.md). `Location.upsert_all` and `CollectionImport::Apply#upsert_lots!` (a bound multi-row `INSERT .. ON CONFLICT`) skip validations on purpose (the reader already checked each row).
- **Collection and lots (specs 004, 006, 021, 026, 029, 032–034, 041, 059, 062, 065; ADRs 0019, 0025, 0028):** a lot's identity (printing, finish, condition, price paid and place, `lot_key`), the 9,999 cap, merging, Move copies, the grid and table, bulk mode and its Undo, number entry, locations and their names, and decks, their zones and the label "Deck › Zone" are in [`docs/architecture/collection-and-lots.md`](docs/architecture/collection-and-lots.md); how the export, preview and apply cover lots, locations and decks is in [`docs/architecture/data-portability.md`](docs/architecture/data-portability.md). Guards an agent trips first: `Location::Name` is the one definition of a name (`spec/models/location/name_parity_spec.rb`); five places build a `lot_key` and all must carry the place; `Account` declares `lots` before `locations` because the restrict foreign key needs lots deleted first (`spec/models/account_spec.rb`); a location has a kind, so a list says which one it means (every picker and the collection filter offer places and zones through `Location::Choices`, and a write names its location through `Location.find_placeable!`; the Locations page and the export stay places only; [`collection-and-lots.md`](docs/architecture/collection-and-lots.md)), and the deck files name no collectible, format or zone key but `considering` (`spec/deck_core_spec.rb`); number entry and the location files name no collectible type (`spec/number_entry_core_spec.rb`, `spec/import_apply_core_spec.rb`).
- **Backup and restore (spec 030, ADR 0024):** what a backup holds, the restore's refusals and the rules of both are in the [release and deploy](docs/architecture/release-and-deploy.md) area doc; `docs/backup-restore.md` has the file's layout, `README.md` the procedure. The two tasks don't depend on `:environment`, so they boot nothing; their code is in `lib/collector/backup/`, required by path and not autoloaded (`config/application.rb`), and opens snapshots with `SQLite3::Database`, never Active Record. The suite's backup examples commit rows (`:committed`, `spec/support/backup_helpers.rb`); a model with a new attachment, or a fifth production database, fails `spec/backup_guards_spec.rb` until the backup's contents are decided.
- **Off-limits for reads (permission-denied):** `.kamal/secrets`, `config/master.key`, `.env*`, `storage/`. Don't try to read them.

## Architecture Intent

- **Collectible-agnostic core.** Core domain models (collections, items, conditions, valuations) must not know about any specific collectible; MTG-specific code lives under the `MTG::` namespace (inflector acronym in `config/initializers/inflections.rb`) behind an extension boundary.
- **Row-level multi-tenancy (spec 004, ADR 0017).** Every tenant-owned table carries `account_id`; requests resolve `Current.account` and all queries scope through it (another account's record is a 404); a job or broadcast on tenant data must carry and restore the account; catalog data is global. First run, sign-in and sessions, the admin users page, the endpoints that skip sign-in and the cross-account reads are in [`docs/architecture/tenancy-and-accounts.md`](docs/architecture/tenancy-and-accounts.md); the coding rules are `.claude/rules/multi-tenancy.md`.
- **External data behind adapters.** Sources such as Scryfall implement the `Catalog::Sources` contract and live in their collectible's namespace (`MTG::Scryfall`); they are synced in background jobs (bulk data, cached locally) and never called during page render.
- **Self-hosting & upgrades.** Separate SQLite DBs (primary/queue/cache/cable) live in `storage/` on a persistent volume. Released migrations are never edited; every migration must be safe to run unattended from any prior version. User data export/import uses a documented, versioned format keyed by external IDs.

## Claude Code Hooks (`.claude/settings.json`)

- At session start in a local session (an Orca worker's too): `.claude/hooks/session-start.sh` puts `.ruby-version`'s Ruby first on the PATH of the session's commands through `$CLAUDE_ENV_FILE`, found with `script/worktree/with_mise --optional`, so a bare `ruby` and `bundle` are 4.0.7 and not macOS's 2.6 (#289); with no mise (CI, containers) it changes nothing, and cloud sessions keep the rbenv path.
- After editing a Ruby file: `bin/rubocop -a` runs on that file; remaining offenses are reported back.
- Before `git commit`: RuboCop on staged Ruby files + Brakeman; failures block the commit.
- Before `git push`: `.claude/hooks/pre_push_ci.rb` (Ruby, no `jq`) runs `bin/ci checks`, skipping RSpec, when the branch is documentation-only and the command is a plain push of the current branch; otherwise, or whenever it can't tell, the full `bin/ci`. It prints which it ran and why; failure blocks the push (spec 035 decision 3, Story 3). Documentation-only means every path the branch changed since its merge base with `origin/main` (both names of a rename) is under `docs/` or is a `.md` file outside `app/`, `bin/`, `config/`, `db/`, `lib/`, `script/`, `spec/` and `vendor/`, and none is under `docs/export-format/` or `.claude/hooks/` or is `.claude/settings.json` or `.claude/settings.local.json`. The rules are code in `lib/collector/push_scope.rb`.
- Both gates also block when they time out (180 s and 900 s): each sets `"onFailure": "block"`, which needs Claude Code 2.1.295 or later; an older Claude Code ignores the key and lets a timed-out hook through, as it did while `bin/ci` ran past 900 s (#145).

## UI and design system

All UI follows the Collector design system in `docs/design-system/`. Before creating or changing any view, partial, stylesheet or UI copy, use the `collector-design-system` skill (`.claude/skills/collector-design-system/SKILL.md`) and read `docs/design-system/README.md`. Use only the token variables and `c-*` classes from `app/assets/stylesheets/collector/`; never hard-code colours, spacing or fonts. The design system is the project's own, in code: new patterns go in `collector/additions.css` with a doc per pattern under `docs/design-system/components/`, and a rule changes in `docs/design-system/README.md`.
